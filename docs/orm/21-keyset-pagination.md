# Keyset pagination

`query.paginate()` returns one page and opaque cursors to the pages next to it. Unlike `skip()`, it does not shift or repeat rows when rows are inserted or deleted between two page requests, and its cost does not grow with the page number.

```ts
const page = await Order.where('Status', 'open').paginate({ orderBy: [['CreatedAt', 'desc']], limit: 50 });
// page.items, page.next, page.previous
const following = await Order.where('Status', 'open').paginate({ orderBy: [['CreatedAt', 'desc']], limit: 50, after: page.next! });
```

- `orderBy` lists columns and directions; directions may be mixed. The primary key is appended as the tie-breaker, so equal values never split or repeat across pages.
- `after: next` continues forward. `before: previous` goes back. `next` is `null` on the last page and `previous` is `null` on the first. An empty page reached with `before` has `next` set to the cursor it was asked with.
- A cursor is base64url JSON of the order values of the row it was made from, plus a hash of the order. A cursor used with another `orderBy`, or one that does not decode, throws `InvalidCursor`. `InvalidCursor` is an `InvalidArgument`, so `@spinajs/http` answers it with 400 `application/problem+json`.
- Each decoded value must fit its column, read from the driver's dialect profile (`nativeTypes`): a safe integer for an integer column (32-bit unless the type also holds bigint), a whole number within int64 for a bigint column, a number for decimal where the driver reads decimals back as numbers (SQL Server, SQLite; a model converter that turns such a decimal into text gets its own cursors refused, so have it return a number or page by another column) and a number or numeric string elsewhere, a time of day for time (hours 0-23, `HH:MM` or `HH:MM:SS` with at most seven fraction digits; an order column whose native type is `time` cannot be paged today: its value hydrates as a `TimeSpan`, which a cursor cannot hold, and the first page with a next page throws `InvalidOperation`, so this rule is reached only by a cursor written by hand and refuses its value before any SQL runs), a string for text and enum, a boolean for boolean, a datetime for date and datetime, a UUID string for uuid. A value that does not fit, or a cursor longer than 4096 characters, throws `InvalidCursor`; so does the next request after a page whose cursor grew past 4096 characters (a text order column of ~3 KB values). Only the family is checked: a range narrower than the family (pg `int2`, `float4`) still reaches SQL, and a mysql `INT UNSIGNED` key above 2^31 is refused as an integer. A column whose type the profile does not list is not checked. On SQL Server, which tests a page's conditions in an order of its own, a forged value that fits its family but not the column (a datetime outside the column's range; any value for a column whose type the dialect profile does not list, such as `money`, `smallmoney`, `smalldatetime` or `sql_variant`, which is not checked at all) can make a page fail depending on rows its `where()` removes, other tenants' rows included; this check does not cover such values, and only a signed cursor would. A value that fits its family but not the column (a label a postgres enum lacks, a NUL character in PostgreSQL text, a datetime outside the column's range) is refused by the database with a `DataException`. `paginate()` then asks the database about the cursor's predicate alone, with one more select of at most one row, and reports `InvalidCursor` only when that is refused too. Inside a transaction the probe cannot run when the page error has already aborted the transaction, and the error stays a `DataException`: on PostgreSQL and PGlite every data error aborts it, and on SQL Server a conversion error (241, 242, 245) does. MySQL, and SQL Server after an arithmetic overflow (220, 8115), convert it there too. A data error from the query's own `where()` or from a populated relation stays a `DataException`, on the first page and on every later one. SQLite coerces values instead of refusing them, so its driver never throws `DataException` and a cursor is never converted there.
- The cursor is spec-checked, not signed. The hash names the order it was made for and carries no secret, so a client can craft a start position; that only moves the start of the page, and the query's own `where()` still bounds the rows a page can reach. Do not rely on a cursor to hide rows: put the restriction in the query.
- The probe that decides between `InvalidCursor` and the page's `DataException` sees the rows the page query may see. It runs with the model's query middlewares (such as tenancy-orm's tenant filter), with the per-query marks a clone of the page query would carry (tenancy-orm's `acrossTenants()`, authz-orm's `accessible()` and `within()`), and with the soft-delete and archive filters. It leaves out the query's own `where()`, which can raise the same error. A page read with `withDeleted()` or `withArchived()` is still probed without those rows; that changes at most which of the two errors is thrown. An error of the probe that is not a database error (`OrmException`), such as an authz or tenant refusal, is thrown as it is. Its query middlewares see it as a statement of its own: a copied `.unscoped(reason)` records the unscoped read once more. What stays open: cursors are not signed, so a forged value that fits its family but not its column still reaches the page query and is refused there. On SQL Server that is a datetime before 1753, a date, datetime2 or datetimeoffset after year 9999, a smalldatetime, money or smallmoney value, or any value of a type the dialect profile does not list; on PostgreSQL an enum label, a NUL in text, an `int2` or `float4` overflow, a date or timestamp outside PostgreSQL's range, json and jsonb, or an unlisted type (refused at bind, whatever the rows); on MySQL and SQLite none. Whether such a refusal ever depends on rows the page's filters remove is up to the database's query plan and is not shown to happen; only a signed cursor would rule it out.
- Order columns must be NOT NULL. A column the model describes as nullable throws `InvalidArgument` before the first page is fetched. A NULL in the row a cursor is made from throws `InvalidOperation`.
- The query must not have its own `order()`, `take()`, `skip()` or `first()`. `paginate()` sets them and executes the query. `distinct()`, `groupBy()` and an aggregate column are refused too (`InvalidOperation`); an order by a relation column is an `InvalidArgument`.
- A query narrowed with `select()` or `columns()` gets the order columns and the primary key added to its column list, because the cursors are made from them. The rows carry those columns at runtime; the row type stays as narrowed.
- Rows present for the whole walk appear exactly once. Rows inserted during the walk appear when they sort after the current position.
