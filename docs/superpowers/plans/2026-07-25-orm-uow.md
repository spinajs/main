# ORM Unit-of-Work Branch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give `@spinajs/orm` a real persistence model — mutate a loaded object graph, call `save()` once, and get one transaction that inserts, updates, links, unlinks and orphan-handles every touched row in foreign-key-safe order.

**Architecture:** Hydration records a **value-copy snapshot** of each model's column values and of each populated relation's member primary keys. `save()` walks the graph from a root model, resolves every reachable model through a **transaction-scoped identity map**, diffs each against its snapshot to produce a **Subject** (model + operation + changed columns + relation deltas), **topologically sorts** the subjects by foreign-key dependency, and hands the sorted plan to an **executor** that runs it inside a single `OrmDriver.transaction()` from `orm-foundation`. A relation that was never populated is invisible to the whole pipeline, which is what makes `Items: OrderItem[] = []` on a freshly constructed model delete nothing.

**Tech Stack:** TypeScript (ESM, dual CJS build), `@spinajs/di` for DI, mocha via `ts-mocha`, chai `expect`, `chai-as-promised`, sinon for spies. SQLite via `sqlite3` for end-to-end coverage, MySQL via `mysql2` for the docker-compose integration suite added by `orm-foundation`.

## APIs from `orm-foundation` this branch builds on

Re-read these before starting; they changed in `9fd6d513d`, `563016b12` and `c1a0f7e79`.

- **`OrmDriver.transaction<R>(cb, options?): Promise<R>`** — [driver.ts:224-261](../../../packages/orm/src/driver.ts#L224). A concrete template method, no longer abstract. It commits when `cb` resolves, rolls back when it throws, disposes in `finally`, and resolves with `cb`'s return value. The old `{ commit, rollback }` return shape is **gone**. A nested call while a transaction is already ambient takes a savepoint ([driver.ts:229-245](../../../packages/orm/src/driver.ts#L229)) rather than opening a second transaction — which is what makes it safe for `save()` to wrap driver-level helpers that themselves open transactions.
- **Seven abstract primitives** — `_begin`, `_commit`, `_rollback`, `_savepoint`, `_releaseSavepoint`, `_rollbackToSavepoint`, `_dispose` ([driver.ts:174-206](../../../packages/orm/src/driver.ts#L174)). This branch adds no driver primitives and implements none.
- **Ambient connection propagation** via `AsyncLocalStorage` on the abstract driver ([driver.ts:43](../../../packages/orm/src/driver.ts#L43)), exposed as `OrmDriver.CurrentTransaction: ITransactionContext | undefined` ([driver.ts:55-57](../../../packages/orm/src/driver.ts#L55)). Every statement the executor issues inside the `transaction()` callback automatically lands on the transaction's connection; nothing is threaded by hand.
- **`Builder.execute()` memoizes** ([builders.ts:148-154](../../../packages/orm/src/builders.ts#L148)); the engine is `protected async _run(): Promise<T>` ([builders.ts:88-141](../../../packages/orm/src/builders.ts#L88)). `then()`/`catch()`/`finally()` delegate to `execute()`. **A builder executes at most once** — the executor must build a fresh builder per statement, never re-await one.
- **`SelectQueryBuilder` overrides `_run()`, not `execute()`** ([builders.ts:1392-1402](../../../packages/orm/src/builders.ts#L1392)), so `beforeQueryExecution` and `takeFirst()` unwrapping land inside the memo.
- **`_compiled` moved up to `OrmRelation`** ([relations.ts:57](../../../packages/orm/src/relations.ts#L57)) and now guards `QueryRelation.compile()` ([relations.ts:218-226](../../../packages/orm/src/relations.ts#L218)) and `VirtualRelation.compile()` ([relations.ts:243-251](../../../packages/orm/src/relations.ts#L243)) too.
- **`ITransactionContext`** is `{ connection?: unknown; depth: number }` ([interfaces.ts:1519-1522](../../../packages/orm/src/interfaces.ts#L1519)). Task 7 adds one optional field to it.

## Spec corrections found while reading the source

The spec is a statement of intent. Where it disagrees with the tree at `6b3a05462`, the tree wins. Each correction below names the file and line that disproves the spec claim.

### C1 — `SingleRelation.populate()` does **not** re-query the owner's row

The spec (§U7) says it "re-queries the owner's entire row to load one relation … with a TODO saying so". The **TODO is stale; the code is not**. [relation-objects.ts:237-239](../../../packages/orm/src/relation-objects.ts#L237) reads:

```ts
const query = createQuery(this.Relation!.TargetModel, SelectQueryBuilder<ModelBase>).query;
const desc = extractModelDescriptor(this.Relation!.TargetModel);
query.where({ [desc!.PrimaryKey]: (this._owner as any)[this.Relation!.ForeignKey] });
```

That is a query on the **target** model keyed by the owner's foreign-key value — exactly what the TODO at [relation-objects.ts:235](../../../packages/orm/src/relation-objects.ts#L235) asks for. `git log -S "const query = createQuery(this.Relation!.TargetModel"` dates the current form to `8a75ee858`; the comment above it dates to `e89504e7a`, older. There is nothing to optimise.

There **is** a real defect at the same site, and Task 27 fixes that one instead: the WHERE column is `extractModelDescriptor(TargetModel).PrimaryKey` — the target model's own primary key — where it must be `this.Relation.PrimaryKey`, the join column the relation declares ([interfaces.ts:470-474](../../../packages/orm/src/interfaces.ts#L470)). A `@BelongsTo(Target, 'fk', 'SomeOtherColumn')` joins on the wrong column today.

### C2 — `Populated` is never set on the eager-loading path, so the anti-footgun flag does not yet distinguish anything

The spec (§3, §U1) leans on `Populated` ([relation-objects.ts:61](../../../packages/orm/src/relation-objects.ts#L61)) to tell "untouched" from "cleared". `grep -rn "Populated" packages/orm/src` returns exactly eight hits, and **every assignment is in `relation-objects.ts`**: lines 251, 288, 295, 446, 509. Those are the lazy `relation.populate()` methods and the two always-populated query-relation constructors.

Nothing sets it on the eager path:

- [middlewares.ts:44-56](../../../packages/orm/src/middlewares.ts#L44) — `HasManyRelationMiddleware` builds the relation list via `DI.resolve(RelationClass, [d, desc, relData])` and never touches `Populated`.
- [middlewares.ts:213](../../../packages/orm/src/middlewares.ts#L213) — `HasManyToManyRelationMiddleware` does `new ManyToManyRelationList(d, self._description, relData)`; same.
- [hydrators.ts:77](../../../packages/orm/src/hydrators.ts#L77) — `OneToManyRelationHydrator` does `new OneToManyRelationList(target, val, mapRel)`; same.
- [hydrators.ts:107](../../../packages/orm/src/hydrators.ts#L107) — `OneToOneRelationHydrator` does `new SingleRelation(target, val.TargetModel, val, tEntity)`; same.

So `await Order.query().populate('Items').first()` leaves `order.Items.Populated === false`, indistinguishable from a freshly constructed model. Building `save()` on the flag as it stands would make it skip every eagerly populated relation — i.e. the headline example in the spec's §2 would do nothing. **Task 4 fixes `Populated` at all four sites before anything depends on it.**

### C3 — the `Object.assign(d)` no-op is at line **278**, and it is in `afterQuery`, not in a snapshot path

Spec §U1 cites `middlewares.ts:278`. Confirmed — [middlewares.ts:278](../../../packages/orm/src/middlewares.ts#L278) is `const transformedData = Object.assign(d);` inside `BelongsToRelationResultTransformMiddleware.afterQuery`. (`docs/orm-analysis.md` line 201 says 277; the file has since gained a line. The plan uses 278.)

But it is **not** on the snapshot path and fixing it does not make snapshots value-copies. It aliases a raw DB **row**, not a model. Fixing it is still correct and still in scope (Task 6); the snapshot's value-copy guarantee is an independent piece of work (Tasks 2, 3, 5) and must not be assumed to fall out of this fix.

### C4 — `IColumnDescriptor.Nullable` exists, but its default is a footgun for the orphan policy

Spec §U5 asks whether nullability is reflected. It is: [interfaces.ts:699](../../../packages/orm/src/interfaces.ts#L699) declares `Nullable: boolean`, populated from `tableInfo()` reflection in [orm.ts:144-168](../../../packages/orm/src/orm.ts#L144). **No descriptor change is needed for nullability.**

The trap is the default. [decorators.ts:23](../../../packages/orm/src/decorators.ts#L23) — `_prepareColumnDesc` defaults `Nullable: false`. A column the model declares but the database has not reflected (or a model used before `Orm.resolve()` has run `reloadTableInfo`) reports `Nullable: false`, so a naive "`nullify`, falling back to `delete` when the FK is non-nullable" would **silently delete rows** whenever table info is missing. Task 8 therefore resolves the fallback as: fall back to `delete` only when the FK column is present in `Columns` **and** reflected (`NativeType !== ''`) **and** `Nullable === false`. An unreflected column keeps `nullify`, which fails loudly at the database instead of destroying data.

- Spec: "`_.uniqBy` … at middlewares.ts:262-268". The HACK comment is 262-266 and the `_.uniqBy` call is at [middlewares.ts:268](../../../packages/orm/src/middlewares.ts#L268).

### C6 — the duplicate-middleware root cause is a shared array, not a double registration

Spec §U7 attributes the `_.uniqBy` workaround to "nested `belongsTo` under `manyToMany` adding the same middleware more than once". The middleware is registered **once**. The duplication is in the *reader*, [middlewares.ts:254-260](../../../packages/orm/src/middlewares.ts#L254):

```ts
const middlewares = ((this.relation as any)._relationQuery.Relations as any[])
  .map((x) => { return x._query._middlewares; })
  .reduce((prev, current) => { return prev.concat(current); }, []);
```

Every relation created on a builder stores that builder as `_query` — see [builders.ts:1189-1208](../../../packages/orm/src/builders.ts#L1189), where `_getRelationInstance` passes `this` as the relation's `_query`. So for **N** nested relations under one `belongsTo`, `x._query._middlewares` is **the same array object N times**, and the `reduce` concatenates it N times. That is why the symptom needs "multiple nested belongs to relation" to appear, exactly as the HACK comment says. Task 24 fixes the reader; no registration site changes.

Secondary hazard at the same site: `_.uniqBy(middlewares, (x) => x._description.Name)` dereferences `_description` unconditionally. `BelongsToRelationResultTransformMiddleware` has no `_description` field at all ([middlewares.ts:275-288](../../../packages/orm/src/middlewares.ts#L275)), and `DiscriminationMapMiddleware._description` is an `IModelDescriptor`, not an `IRelationDescriptor` ([discrimination-middleware.ts:6](../../../packages/orm/src/discrimination-middleware.ts#L6)) — so the key silently compares a *model* name against a *relation* name. Task 24's replacement keys on object identity and never dereferences `_description`.

### C7 — `PrimaryKeyValue`'s setter propagates the new key to `RelationType.One` incorrectly

Not named by the spec, but the executor's key-backfill step lands on it. [model.ts:133-136](../../../packages/orm/src/model.ts#L133):

```ts
case RelationType.One:
  (rel as any)[r.ForeignKey] = newVal;
  break;
```

`rel` is the owner's `SingleRelation` wrapper, and for a `belongsTo` the foreign key lives on the **owner**, not on the relation object or the target. This writes a stray property onto the wrapper and has no effect on anything persisted. The `RelationType.Many` branch at [model.ts:137-139](../../../packages/orm/src/model.ts#L137) *is* correct (it stamps the owner's new key onto each child's FK column). The executor must therefore **not** rely on the setter for `belongsTo` back-fill and does its own explicit resolution (Task 15). Leaving the setter alone is deliberate — changing it is a behaviour change with no test coverage and no bearing on `save()`.

### C8 — spec deviations recorded up front

Two places where the spec is underspecified and this plan chooses:

1. **Executor step 5, "Deletes".** With orphan policies driving every removal, there is no second source of deletions in this branch's API surface — `save()` has no `markForDeletion()`. Steps 4 and 5 of spec §U5 therefore collapse into one ordered orphan phase: nullify/soft-delete `UPDATE`s first, then `DELETE`s in reverse topological order. Explicit deletion of a graph member stays out of scope.
2. **"become individually transactional" (spec §U6).** Wrapping a single-statement operation in `BEGIN`/`COMMIT` buys no atomicity and costs a round-trip pair. Task 28 wraps only the genuinely multi-statement paths — `OneToManyRelationList.sync`/`update`, `ManyToManyRelationList.sync`/`update`, `SingleRelation.set`/`remove` — and documents that `ModelBase.insert`/`update`/`destroy`/`insertOrUpdate` are already atomic because each is one statement.

## Phase 1 — Snapshot and identity map (U1, U2)

### Task 2: Snapshot primitives

**Files:**
- Create: `packages/orm/src/snapshot.ts`
- Test: `packages/orm/test/snapshot.test.ts` (create)

**Interfaces:**
- Consumes: `IColumnDescriptor`, `IModelDescriptor` from `packages/orm/src/interfaces.ts`.
- Produces:

```ts
// packages/orm/src/snapshot.ts
export interface IModelSnapshot {
  /** Column name -> value copy taken at hydration time. */
  Columns: Map<string, unknown>;
  /** Relation name -> member primary keys captured when the relation was populated. */
  Relations: Map<string, unknown[]>;
}

export function createSnapshot(): IModelSnapshot;
export function snapshotValue(value: unknown): unknown;
export function snapshotEquals(a: unknown, b: unknown): boolean;
export function snapshotFromRow(descriptor: IModelDescriptor, row: Record<string, unknown>): Map<string, unknown>;
```

**Why a value copy and not a reference.** If `snapshotValue` returns its argument for a mutable value, a later in-place mutation of that value mutates the snapshot too, the diff comes out empty, and `save()` silently does nothing. That is the exact failure mode `docs/orm-analysis.md` line 201 already records elsewhere in this codebase. The tests below assert immutability **directly** — they mutate the source and re-read the snapshot — rather than inferring it from `save()` behaviour.

- [ ] **Step 1: Write the failing test**

Create `packages/orm/test/snapshot.test.ts`:

```ts
/* eslint-disable prettier/prettier */
import { expect } from 'chai';
import 'mocha';
import { DateTime } from 'luxon';
import { createSnapshot, snapshotEquals, snapshotValue } from '../src/snapshot.js';

describe('snapshot primitives', () => {
  describe('snapshotValue', () => {
    it('returns primitives unchanged', () => {
      expect(snapshotValue(1)).to.equal(1);
      expect(snapshotValue('a')).to.equal('a');
      expect(snapshotValue(true)).to.equal(true);
      expect(snapshotValue(null)).to.equal(null);
      expect(snapshotValue(undefined)).to.equal(undefined);
    });

    it('copies an array so mutating the source does not change the copy', () => {
      const source = [1, 2, 3];
      const copy = snapshotValue(source) as number[];

      source.push(4);
      source[0] = 99;

      expect(copy).to.deep.equal([1, 2, 3]);
      expect(copy).to.not.equal(source);
    });

    it('copies a plain object so mutating the source does not change the copy', () => {
      const source = { a: 1, nested: { b: 2 } };
```

```ts
/* eslint-disable prettier/prettier */
import _ from 'lodash';
import { DateTime } from 'luxon';
import { IModelDescriptor } from './interfaces.js';

/**
 * The diff baseline for one model instance.
 *
 * `Columns` holds a *value copy* of every column at the moment the model was hydrated from
 * the database. `Relations` holds, per relation name, the primary keys of the members that
 * were present when that relation was populated.
 *
 * Both must be copies. If a snapshot aliases live state, a later mutation changes the
 * baseline as well, the diff is empty, and `save()` silently does nothing.
 */
export interface IModelSnapshot {
  Columns: Map<string, unknown>;
  Relations: Map<string, unknown[]>;
}

export function createSnapshot(): IModelSnapshot {
  return {
    Columns: new Map<string, unknown>(),
    Relations: new Map<string, unknown[]>(),
  };
}

/**
 * Takes a value copy suitable for a diff baseline.
 *
 * Immutable values (primitives, luxon `DateTime`) are returned as-is. Everything the ORM can
 * put in a column and that can be mutated in place — `Buffer` (binary/UUID columns), `Date`,
 * arrays and plain objects (JSON columns) — is copied. Class instances the ORM does not own
 * are returned as-is: cloning them could break invariants, and a converter that produces one
 * is responsible for its own equality via `snapshotEquals`.
 */
export function snapshotValue(value: unknown): unknown {
  if (value === null || value === undefined) {
    return value;
  }

  if (typeof value !== 'object') {
    return value;
  }

  if (DateTime.isDateTime(value)) {
    // luxon DateTime is immutable; every "mutation" returns a new instance.
    return value;
  }

  if (Buffer.isBuffer(value)) {
    return Buffer.from(value);
  }

  if (value instanceof Date) {
    return new Date(value.getTime());
  }

  if (Array.isArray(value) || _.isPlainObject(value)) {
    return _.cloneDeep(value);
  }

  return value;
}

/**
 * Value equality for a diff. Deliberately stricter than `==`: `null` and `undefined` are
 * different (one is "explicitly cleared", the other "never set"), and `0`/`''`/`false` are
 * never equal to each other.
 */
export function snapshotEquals(a: unknown, b: unknown): boolean {
  if (a === b) {
    return true;
  }

  if (a === null || a === undefined || b === null || b === undefined) {
    return false;
  }

  if (DateTime.isDateTime(a) && DateTime.isDateTime(b)) {
    return a.toMillis() === b.toMillis();
  }

  if (a instanceof Date && b instanceof Date) {
    return a.getTime() === b.getTime();
  }

  if (Buffer.isBuffer(a) && Buffer.isBuffer(b)) {
    return a.equals(b);
  }

  if (typeof a === 'object' && typeof b === 'object') {
    return _.isEqual(a, b);
  }

  return false;
}

/**
 * Builds a column snapshot straight from a raw database row, applying the same converters
 * hydration applies. Used by `save({ reload: true })`, which needs the *database's* current
 * values as the baseline without disturbing the user's in-memory edits.
 */
export function snapshotFromRow(descriptor: IModelDescriptor, row: Record<string, unknown>): Map<string, unknown> {
  const columns = new Map<string, unknown>();

  for (const c of descriptor.Columns ?? []) {
    if (!(c.Name in row)) {
      continue;
    }

    const raw = row[c.Name];
    const converted = c.Converter ? c.Converter.fromDB(raw, row, descriptor.Converters.get(c.Name)?.Options) : raw;

    columns.set(c.Name, snapshotValue(converted));
  }

  return columns;
}
```

```ts
  /**
   * The diff baseline for this instance, or `null` when it has never been hydrated from
   * the database. Read-only from the outside: mutate it only through `takeSnapshot()`,
   * `snapshotRelation()` and `clearSnapshot()`.
   */
  public get Snapshot(): IModelSnapshot | null {
    return this.__snapshot__;
  }

  /**
   * Captures the current value of every column as the diff baseline, discarding any
   * previous baseline and any relation keys recorded against it.
   *
   * Values are copied, never aliased — see `snapshotValue`. An aliased snapshot makes
   * every diff empty and `save()` a silent no-op.
   */
  public takeSnapshot(): void {
    const snapshot = createSnapshot();

    for (const c of this.ModelDescriptor?.Columns ?? []) {
      snapshot.Columns.set(c.Name, snapshotValue((this as any)[c.Name]));
    }

    this.__snapshot__ = snapshot;
  }

  /**
   * Records the primary keys of the members currently in relation `name` as that
   * relation's baseline. A no-op when the model has no snapshot — an unhydrated model
   * has nothing to diff against and its relations are all "new".
   *
   * @param name - relation property name, as declared on the model descriptor
   */
  public snapshotRelation(name: string): void {
    if (!this.__snapshot__) {
      return;
    }

    const relation = (this as any)[name];

    if (relation === null || relation === undefined) {
      return;
    }

    if (relation instanceof SingleRelation) {
      const value = relation.Value;
      this.__snapshot__.Relations.set(name, value ? [value.PrimaryKeyValue] : []);
      return;
    }

    if (typeof relation[Symbol.iterator] === 'function') {
      this.__snapshot__.Relations.set(name, [...(relation as Iterable<ModelBase>)].map((m) => m.PrimaryKeyValue));
    }
  }

  /**
   * Discards the diff baseline. After this the model is treated as brand new by `save()`.
   */
  public clearSnapshot(): void {
    this.__snapshot__ = null;
  }

  /**
   * Names of the columns whose current value differs from the snapshot.
   *
   * With no snapshot every column is reported as changed, which is the right answer for a
   * model that is about to be inserted.
   *
   * This is deliberately independent of `__dirty_props__`: the proxy records a property as
   * dirty on any write, including one that puts the original value back, so the snapshot
   * diff is the more precise answer and the one the UPDATE payload is built from.
   */
  public changedColumns(): string[] {
    const columns = this.ModelDescriptor?.Columns ?? [];

    if (!this.__snapshot__) {
      return columns.map((c) => c.Name);
    }

    const snapshot = this.__snapshot__;
    return columns.filter((c) => !snapshotEquals(snapshot.Columns.get(c.Name), (this as any)[c.Name])).map((c) => c.Name);
  }

  /**
   * Records `prop` as changed and marks the model dirty.
   *
   * This is the supported way for relation objects to report that they rewrote one of the
   * owner's foreign keys. It replaces the `(owner as any).__dirty_props__.push(...)` casts
   * that reached into a private field from outside the class ( A6 ).
   *
   * @param prop - column name
   */
  public markDirty(prop: string): void {
    if (!this.__dirty_props__.includes(prop)) {
      this.__dirty_props__.push(prop);
    }

    this.IsDirty = true;
  }
```

Note the ordering inside `markDirty`: `IsDirty = true` must come **after** the push, because the `IsDirty` setter clears `__dirty_props__` when assigned `false` ([model.ts:69-74](../../../packages/orm/src/model.ts#L69)) — assigning `true` does not clear, but keeping the push first makes the method order-independent if that setter ever changes.

No other middleware captures a reference to the pre-transform rows: `DiscriminationMapMiddleware.afterQuery` and `BelongsToPopulateDataMiddleware.afterQuery` both return `data` unchanged ([discrimination-middleware.ts:8-10](../../../packages/orm/src/discrimination-middleware.ts#L8), [middlewares.ts:246-248](../../../packages/orm/src/middlewares.ts#L246)).

```ts
/* eslint-disable prettier/prettier */
import { Constructor } from '@spinajs/di';
import { IIdentityMap } from './interfaces.js';
import type { ModelBase } from './model.js';

/**
 * Renders a primary-key value as a Map key.
 *
 * Type-tagged so `1` and `'1'` never collide — a string key column and an integer key column
 * on two different models could otherwise alias each other through a shared cache. Returns
 * `null` for an absent key: a model with no primary key cannot be identified and is never
 * registered.
 *
 * @param pk - primary key value
 */
export function identityKey(pk: unknown): string | null {
  if (pk === null || pk === undefined) {
    return null;
  }

  if (Buffer.isBuffer(pk)) {
    return `b:${pk.toString('hex')}`;
  }

  return `${typeof pk}:${String(pk)}`;
}

/**
 * Maps `(model constructor, primary key) -> instance` for the duration of one `save()` graph
 * walk, or of one transaction when several saves run inside it ( overview decision D7 ).
 *
 * Its only job is to guarantee that a row reached through two relation paths produces one
 * subject rather than two conflicting ones. It is **not** a cache: nothing outside a
 * `save()` consults it, it is discarded when the transaction ends, and queries behave
 * exactly as they did before.
 *
 * Keyed by constructor identity rather than class name — name-based lookup breaks under
 * minification and when two connections declare models with the same class name ( A9 ).
 */
export class IdentityMap implements IIdentityMap {
  private _entries = new Map<Constructor<ModelBase>, Map<string, ModelBase>>();

  private _size = 0;

  public get Size(): number {
    return this._size;
  }

  public get(model: Constructor<ModelBase>, pk: unknown): ModelBase | undefined {
    const key = identityKey(pk);
    if (key === null) {
      return undefined;
    }

    return this._entries.get(model)?.get(key);
  }

  public has(model: Constructor<ModelBase>, pk: unknown): boolean {
    return this.get(model, pk) !== undefined;
  }

  /**
   * Registers `model` and returns the canonical instance for its identity — the one already
   * registered if there is one, otherwise `model` itself. A model with no primary key is
   * returned unchanged and not registered: it has no identity yet.
   *
   * @param model - model to canonicalize
   */
  public add(model: ModelBase): ModelBase {
    const key = identityKey(model.PrimaryKeyValue);
    if (key === null) {
      return model;
    }

    const ctor = model.constructor as Constructor<ModelBase>;
    let byKey = this._entries.get(ctor);

    if (!byKey) {
      byKey = new Map<string, ModelBase>();
      this._entries.set(ctor, byKey);
    }

    const existing = byKey.get(key);
    if (existing) {
      return existing;
    }

    byKey.set(key, model);
    this._size += 1;

    return model;
  }

  public clear(): void {
    this._entries.clear();
    this._size = 0;
  }
}
```
