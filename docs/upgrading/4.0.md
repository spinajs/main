# Upgrading to 4.0

4.0 resets the foundation: ESM only, Node 22 or newer, one flat `lib/` output, `application/problem+json` error bodies, and a changesets-based release process. Most of the mechanical changes are applied by a codemod. For the features 4.x adds and a path from build to deploy, see [What is new in 4.x](../whats-new-4.0.md).

## Run the codemod first

```bash
npm i -D @spinajs/codemods
npx spinajs upgrade --to 4 --dry-run   # list the files that would change
npx spinajs upgrade --to 4             # rewrite them
```

Run it from the package root (the directory with `tsconfig.json`). It covers the `lib/mjs` import paths, `DI.setESMModuleSupport()` and the `typeof module` cjs/mjs switch, and leaves a `// TODO(spinajs-4)` above every `@HandleException` usage and above every middleware hook listed under [HTTP middlewares](#http-middlewares) that 4.0 removed or changed (`before()`/`after()` of a server middleware, `onResponse` and positional `onBefore`/`onAfter` of a route middleware). Everything else on this page is manual. `@spinajs/codemods` is an optional peer dependency of `@spinajs/cli`; without it `spinajs upgrade` tells you to install it.

## ESM only, Node 22

- Node 22 or newer is required: every package has `engines.node >=22.0.0`. CI tests on 22 and 24.
- Packages are ESM only (`"type": "module"`). `require('@spinajs/...')` no longer resolves; use `import`. The `exports` maps have no `require` condition.
- Your own app must be ESM too: `"type": "module"` in `package.json`, `module` and `moduleResolution` set to `node16` or `nodenext`, and `.js` extensions on relative imports.

## `lib/` paths

Packages build into `lib/` instead of `lib/mjs` and `lib/cjs`.

| Before | After |
| --- | --- |
| `@spinajs/http/lib/mjs/index.js` (or `/index`) | `@spinajs/http` |

Package `exports` maps expose only the package root (`.`), so a deep path such as `@spinajs/orm/lib/config/orm.js` does not resolve under `node16`/`nodenext`. The codemod therefore works like this:

- `lib/mjs` or `lib/mjs/index.js` becomes the package root.
- A deep path becomes the package root only when it is a named import or `export { ... } from` and the installed package's root entry exports every one of those names.
- Any other deep path (side-effect, default or namespace import, `import()`, `require()`, names the root does not export) and every `lib/cjs` path is left as is, gets a `// TODO(spinajs-4)` line above it and is listed at the end of the run. For a file-system lookup such as a config directory, keep the path and build it without `mjs`; otherwise import from the package root.

Static imports, `export ... from`, `import()`, `require()`, `import x = require()` and `typeof import()` with a string literal are covered. Check by hand anything that builds such a path from parts, for example a `system.dirs.*` override that joins `'lib'`, `'mjs'` and a folder: drop the `mjs` segment. The codemod removes the common `typeof module !== 'undefined' ? 'cjs' : 'mjs'` form of this when it is a call argument or a plain string; where dropping the segment would leave an empty path part (a template or a concatenation) it leaves the expression and lists it.

The codemod visits only files that `tsconfig.json` selects through `include`/`files`, JS and CJS files among them even without `allowJs`. Files outside it (for example a root `config.cjs`) must be added to `include` for the run. A file a transform fails on is left untouched and listed; the rest of the run continues.

## `DI.setESMModuleSupport()` is deprecated

It is a no-op that logs a deprecation warning and is removed in 5.0. Delete the call.

## Error bodies are `application/problem+json`

HTTP error responses follow RFC 9457. The body holds `type`, `title`, `status`, `detail`, `instance` and, when present, `code` or `errors`.

- Read `detail` instead of `message`, and `errors` instead of `details` / `parameter`.
- Other properties of an exception are no longer copied into the body. List the ones a client needs in `http.errors.includeFields`, or declare them in a static `problemFields` on the exception class (preferred).
- The stack is added only when `http.errors.includeStack` is `true` outside production (default `false`).
- In production an unmapped 500 answers `detail: "Internal server error"` without `code`; the message stays in the log.
- `ProblemDetails`, `toProblem` and `PROBLEM_DETAILS_SCHEMA` are exported from `@spinajs/http`. The http-swagger error component is now `ProblemDetails`.

`@HandleException` handlers keep working; the codemod only marks them so you re-check the body they produce.

## Config arrays replace the default

An array your app configures now replaces the array a package config sets, as a scalar does. 3.x concatenated every array of every source.

```js
// @spinajs/http-socket ships  http: { socket: { transports: ['websocket', 'polling'] } }
// config/http.js in your app:
export default { http: { socket: { transports: ['websocket'] } } };

// 3.x: ['websocket', 'polling', 'websocket'], which the uniqueItems schema check refuses
// 4.0: ['websocket']
```

The config files now merge in two layers. Package config files of every format (`.js`, `.cjs`, `.json`), common then environment files, come first. Your own config files, `src/config` included, common then environment files, come on top.

| Merge | Arrays |
| --- | --- |
| Package config files (`node_modules/@spinajs/*/lib/config`, or the manifest's `configFiles`) among themselves | concatenate |
| `__configuration__` DI values, which lead the package layer | concatenate |
| Your own config files, over the packages and over each other, also an environment file over a common file | replace |
| `onLoad()`, `StaticConfigurationSource`, `ConfiguratioDbSource` and every other `ConfigurationSource`, `mergeSource()` | replace, in `Order` |
| `configuration.merge(path, value)` | concatenate |

Sources merge in `Order`. `StaticConfigurationSource(cfg)` defaults to `Order` `0`, below the file sources (`1`), so a package default replaces its array, where 3.x kept both. Give it an `Order` above `1` to override a package array: `StaticConfigurationSource(cfg, 10)`.

The layers move scalars too:

- A value in `<cwd>/src/config` now wins over a package default. It used to merge before the packages, so the package won.
- A package environment file (`*.prod.js`) no longer wins over your common file. It used to, because environment files merged after every common file.
- A package JSON file no longer wins over your JS config. Between your own files, JSON still wins over JS.
- In a composed array your entries now follow every package entry, package environment files included.
- A `__configuration__` DI value is a package default. It used to merge after `onLoad()` and win every scalar; now your files, a source above the file sources and `onLoad()` win. Use `configuration.set()` for a value that must win at runtime, also in the browser.

Some arrays collect entries from several packages and your app. They keep concatenating in every merge, so your entries are added to the packages' entries. The list is exported as `COMPOSED_CONFIG_ARRAYS` from `@spinajs/configuration`:

- `system.dirs.*`
- `fs.providers`, `queue.connections`, `http.Static`, `logger.filters`
- the `grants`, `extends` and `revoke` of an RBAC role (`authz.rbac.roles.<role>.grants`) and `authz.rbac.serviceRoles.<service>`
- `authz.abac.policies`, `authz.admin.guard.keepHolders`, `authz.fields.neverRead`, `validation.strict.idPrefixes`
- the `__file__` list of every section

What to check:

- **`http.middlewares`.** A config file or `onLoad()` that lists one middleware now drops the shipped `helmet`. (Compression, the body parsers and the cookie parser are not in the list any more: they are server middlewares, see below.) The app loses its security headers, and `HttpServer` logs one warning at boot. Keep the defaults with `middlewares: [...defaultMiddlewares(), requestId]`, or add to the list with `merge()` (below). The warning recognises the shipped handlers by a tag, so your own `helmet()` also triggers it: ignore it then. A list with its own `cookieParser()` needs the secret too, `cookieParser(secret)`: 3.x kept the shipped parser next to it, and without the secret the signed session cookie is not read and every session answers 401.
- **`http.upload.middlewares`.** The shipped list is `['FileInfoMiddleware']`. A list of only your own upload middlewares drops it, and a route with `fileInfo: true` gets no `file.Info`. List it with yours: `upload: { middlewares: ['FileInfoMiddleware', MyUploadMiddleware] }`.
- A config file or `onLoad()` that listed only the entries it adds to another package array (`http.socket.transports`, `intl.locales`, `telemetry.buckets`, `templates.*.static.portRange`, ...) now drops the package's entries. List the whole array.
- An environment file (`*.prod.js`) that added entries to an array of the common file now replaces it. List the whole array there too.
- To add to a package array instead, call `merge()`, for example in a `configure()` hook: `this.merge('http.middlewares', [requestId])`. `merge()` also appends to an array stored at the path itself now; it used to overwrite it index by index.
- `authz.rbac.roles.<role>.scopeTypes` is a value: your list replaces the shipped one, where 3.x added to it. It can now narrow a role.
- **Files generated by `spinajs-authz-convert`.** A `*-generated.<env>.ts` file written on 3.x holds only what the environment added to an array. Loaded by 4.0 it replaces the common list instead: with `protectedRoles: ['finance']` there, the `system` and `auditor` holders of the common file can be impersonated in that environment. Run the converter again, or add the common entries to every array in those files.
- `BaseFileSource.configFiles()` returns `{ file, arrays }` entries instead of paths, and `projectConfigDirs()` returns one list. A subclass that overrides `configFiles()` must return the new shape. A file source of your own format stays a plain source unless it implements `LoadLayers()` (see [Config files](../configuration/03-config-files.md#basefilesource-custom-file-format)).
- A subclass of `JsFileSource` or `JsonFileSource` that overrides only `Load()`, for example to decrypt values, loads as if it did not: the boot calls `LoadLayers()` of a file source, not `Load()`. The boot logs a warning naming the class. Override `LoadLayers()` instead and change the layers it returns.

## Authentication (`@spinajs/authn`)

`authn.mfa.policy.methods` and `authn.mfa.policy.forceForRoles` are no longer shipped as defaults; the schema defaults apply (`['password']` and `[]`). Config arrays used to concatenate, so a shipped value could not be removed. Now an app that sets `methods` gets exactly its list: a configured list replaces the default.

If you set `methods` without `password` (for example `['oidc']`), password logins no longer require an MFA step. Write `['password', 'oidc']` to keep it. A malformed string `forceForRoles` is now refused instead of being concatenated into a list.

One client address ([Client IP](../http/17-client-ip-and-trust-proxy.md#one-client-address-with-authn)):

- `@spinajs/authn-http` registers `AuthnRealIp` over http's `RealIp`: `authn.http.trustProxy` now also decides `req.storage.realIp`, so `@RateLimit`, `http.throttle`, `@Ip()` and the same-origin and CSRF guards count the client authn counts. An app that set only `authn.http.trustProxy` used to rate limit every client as the proxy.
- `ClientIp` moves to Order 2, after every `RealIp`, copies `req.storage.realIp` and parses no trust. A subclass of `ClientIp` that changed the address moves to a subclass of `AuthnRealIp` registered `.as(RealIp)`.
- A `RealIp` subclass of your own replaces `AuthnRealIp` and ignores `authn.http.trustProxy`: extend `AuthnRealIp` instead. With `authn.http.trustProxy` set, such a subclass fails the boot; without it, the boot warns.
- `CsrfOriginGuard` takes the own origin from the trust `RealIp` stored for the request (`requestProxyTrust(req)`) and no longer parses the trust keys itself.
- `authn.throttle.ipv6Prefix` has no shipped default: unset, it takes `http.throttle.ipv6Prefix`, else 64. Nothing changes unless you set only the http key.
- The boot warns when `authn.http.trustProxy` and `http.trustProxy` are both set and differ, and when `authn.throttle.ipv6Prefix` differs from `http.throttle.ipv6Prefix`. Keep one of each, preferably the http key.
- `@spinajs/http-socket` takes the handshake client address from the registered `RealIp` (`clientAddress()`) instead of parsing `authn.http.trustProxy` and `http.trustProxy` itself. A socket and a request from one client now get one address, and a `RealIp` subclass of your own (another trust, a CDN header) counts for sockets too. Without `@spinajs/authn-http`, `authn.http.trustProxy` no longer moves the socket address: set `http.trustProxy`.
- Import `@spinajs/authn-http` before the socket server starts. `SocketServer` keeps the `RealIp` it resolved at start; loaded later, authn-http logs an error, and sockets ignore `authn.http.trustProxy` until authn-http is imported before the socket server starts.
- `OidcLogoutExtension` reads the trust `RealIp` stored for the request: its protected `OwnTrust` and `SharedTrust` members are removed. A subclass that read them reads `requestProxyTrust(req)`.

### Authentication events go to listeners

`AuthnEventSink` is removed. A class that reacted to authentication events extends `AuthnEventListener` and renames `publish(e)` to `on(e)`:

```ts
@Injectable(AuthnEventListener)
export class LoginAlerts extends AuthnEventListener {
  public async on(e: AuthnEvent): Promise<void> {
    if (e.type === 'login' && e.outcome === 'failure') await notify(e);
  }
}
```

A class that recorded events (to a log, a table, another system) is not needed any more: `@spinajs/audit-authn` records them in the audit trail, and a destination of your own is an `AuditStore` named as the trail's `store`. `RecordingEventSink` of `@spinajs/authn-testing` is `RecordingEventListener`; the dependency `sinks` of `LocalPasswordService`, `TotpService`, `WebAuthnPasskeyService` and `FakeAuthnService` is `listeners`; `WebhookAuthnEventSink`, `SseSessionEndSink` and `QueueAuthnEventSink` are `WebhookAuthnEventListener`, `SseSessionEndListener` and `QueueAuthnEventListener`.

A listener may also implement `ready()`, awaited when `AuthnAudit` resolves (a throw fails the boot), and `flush()`, awaited by `AuthnAudit.settled()`.

- `authn.audit.sinkTimeoutMs` is `authn.audit.listenerTimeoutMs`. The old key is refused at boot as an unknown key.
- `AuthnAudit.sinks()` is `AuthnAudit.listeners()`; `AuthnAudit.over(sinks, { sinkTimeoutMs })` is `AuthnAudit.over(listeners, { listenerTimeoutMs })`.
- `publish`, `publishIn`, `publishDetached` and `settled` of `AuthnAudit` are unchanged.
- New: a listener whose `blocking` getter answers `true` is awaited before the others, and when it fails or runs out of `authn.audit.listenerTimeoutMs` on a success event, the operation fails with `AuthnListenerFailed` (HTTP 503, code `authn_listener_failed`) and a session it has just issued is revoked. `publish` and `publishIn` can therefore reject; with no blocking listener registered they never do, as in 3.x. Failure events and `publishDetached` are never stopped. The events of a login (`login`, `session.issue`), an MFA completion and a step-up reach the listeners that are not blocking only after the blocking ones took all of them (`AuthnAudit.holdIn`), so a stopped login sends no webhook and no `UserLogged`.

### `@spinajs/authn` no longer logs authentication events

`LogAuthnAuditSink` is removed, and `@spinajs/authn` writes authentication events nowhere by itself. Install `@spinajs/audit-authn` and import it: it records every event as a `security` event of the audit trail.

- **No boot warning tells you.** `AuthnAudit` warns at boot only when no listener is registered. An app that registers another one (the queue events of `@spinajs/users`, the SSE session end of `@spinajs/authz-http`, the webhooks of `@spinajs/authn-http`) boots without a warning and records no authentication event until it installs `@spinajs/audit-authn`.
- **To keep them in the log**, nothing else is needed. The default `security` trail writes one line per event on the logger `audit.security`, identifiers as keyed hashes. The line has the audit trail's format, and its hashes are made with `audit.hashKey.secret`, so they differ from the ones in older log files. Log parsers built on `authn audit <type> ...` need the new format, and log routing needs the new logger: the event lines are on `audit.security` (`audit.<trail>` for another log trail). A rule that routed the `authn-audit` logger now gets only listener failures, the boot warning about no listener and failed session revocations.
- **`authn.audit.hashIdentifiers` is removed** and refused at boot. Hashing belongs to the trail: `audit: { trails: { security: { hash: [] } } }` shows identifiers (an id holding `@` stays hashed in a log).
- **`authn.audit.hashKey`** stays, as the row-key secret of `DbAuthnThrottle` only. Set `audit.hashKey.secret` for stable event hashes.
- **A trail with `onFailure: 'reject'` blocks.** The recorder is then a blocking listener: an authentication success whose event cannot be written after the trail's retries fails with HTTP 503 and issues no session; failed attempts and per-request token or key use are never stopped. The default `security` trail continues and never blocks.
- **For a login history that can be queried**, point the recorder at a table trail:

  ```ts
  export default {
    audit: {
      trails: { logins: { store: 'TableAuditStore', table: 'audit_logins', retentionDays: 365 } },
      authn: { trail: 'logins' },
    },
  };
  ```

  `audit().trail('logins').of({ type: 'user', id })` returns what happened to one account.

### Authn routes are rate limited by default

The anonymous routes of `@spinajs/authn-http` and the OIDC begin and callback routes of `@spinajs/authn-oidc` ship a `@RateLimit` each, switched on: a fixed-window cap per client address, for example 30 logins a minute on `POST /auth/login`, 10 registrations an hour on `POST /auth/register`, 60 a minute on each OIDC route. A client over the limit gets the answer the route already gives a throttled client (the uniform 401 login failure with `Retry-After` on the credential routes, the route's 429 `throttled` elsewhere); no `X-RateLimit-*` headers are sent. Back-channel logout is never limited. The full list: [authn-http rate limits](../authn-http/25-rate-limits.md), [authn-oidc rate limits](../authn-oidc/13-rate-limits.md).

- Many users behind one address (an office, a campus, a mobile carrier-grade NAT) share one budget. Raise a limit with `authn.http.rateLimit.<name>: { limit: 120 }` (or `authn.oidc.rateLimit.<name>`), or set `false` to take it off a route.
- Behind a reverse proxy, set `http.trustProxy` (or `authn.http.trustProxy`), or every client shares the proxy's address and one budget.
- With several instances, register a shared `ThrottleStore`; `MemoryThrottleStore` counts per process.
- An end-to-end suite that logs in many times from one address will hit the limits: raise them in its test config.
- If you copied the former recommended `http.throttle` rules for `/auth/*`, keep one coarse `/auth` rule, `headers` left unset, and drop the per-path ones ([the two layers](../http/18-throttling.md#rate-limits-for-the-authn-routes)).
- A global `RateLimitMiddleware` floor in `http.routes.middlewares` no longer applies to these routes: a route's own `@RateLimit` replaces it.

## Rate limits on routes with a session

The routes with a session that spend something per call now carry a config-backed `@RateLimit`, on by default. A client over a limit is refused before the action runs. Every limit is a config key: an object `{ limit?, windowSeconds?, by? }` changes the numbers, `false` takes the limit off the route.

| Package | Config keys | Page |
| --- | --- | --- |
| `@spinajs/authn-http` | `authn.http.rateLimit.{mfaVerify, mfaChallenge, mfaStepUp, reauth, activeRole, impersonate, passwordChange, verifyRequest, tokens, keys, passkeys, mfaEnrolment, adminPasswordReset, adminCredentials}` | [Rate limits of the routes with a session](../authn-http/26-session-route-rate-limits.md) |
| `@spinajs/authn-oidc` | `authn.oidc.rateLimit.{link, reauth}` | [Rate limits of the link and reauth routes](../authn-oidc/14-session-route-rate-limits.md) |
| `@spinajs/authz-http` | `authz.http.rateLimit.{checks, events, explain}` | [Rate limits](../authz-http/11-rate-limits.md) |
| `@spinajs/authz-http-admin` | `authz.http.admin.rateLimit.{commands, writes}` | [Rate limits](../authz-http-admin/08-rate-limits.md) |
| `@spinajs/users-http` | `users.http.rateLimit.{create, security, list, metadata}` | [Rate limits](../users-http/12-rate-limits.md) |
| `@spinajs/teams-http` | `teams.http.rateLimit.{create, invite, resend, accept}` | [Rate limits](../teams-http/README.md#rate-limits) |

- The MFA routes of a pending session count that session (an HMAC of its handle); the others count the principal. **An impersonator spends the impersonated user's budget**: while impersonating, the principal is the user.
- No authn or OIDC route sends `X-RateLimit-*` headers. The routes that check a code or a password answer a throttled request as their service throttle does (the 401 login failure; the 202 of `mfa/challenge`), the other authn routes with authn's 429 `throttled` body, the OIDC link and reauth routes with the OIDC failure answer (303 for a navigation, 401 otherwise); the other packages answer the 429 `E_TOO_MANY_REQUESTS` body with the `X-RateLimit-*` headers.
- `MemoryThrottleStore` counts per process. Behind several instances, register a shared `ThrottleStore`, or each instance allows the full limit.
- An integration test or a batch job that calls one of these routes more often than its limit sets a higher limit, or `false`, in its config.

## HTTP middlewares

Route and server middlewares share one contract: `HttpMiddleware`, with the optional context hooks `onBefore(ctx)`, `onAfter(ctx)`, `onFinish(ctx)` and `onAround(ctx, proceed)`. `RouteMiddleware` and `ServerMiddleware` extend it. The migration tables are in [Route middlewares](../http/14-route-middlewares.md#migrating-from-the-positional-hooks) and [Server middlewares](../http/15-server-middlewares.md#migrating-from-before-and-after).

Route middlewares:

- The hooks take one context object: `onBefore(req, res, route, controller)` becomes `onBefore(ctx)` and `onAfter(req, res, route, controller)` becomes `onAfter(ctx)`. The positional signatures no longer compile.
- `onResponse` is removed. A middleware that still defines it, itself or through a base class, fails the route registration with `RouteRegistrationException`. Move the code to `onAfter(ctx)`: the reply is `ctx.response`, its body `ctx.response.data`.
- `onAfter` runs for every reply of a matched route, error replies included (`ctx.error` is set), and in the exact reverse of the entry order: a route's middleware before the controller's, an inner one before an outer one. A hook meant for successful replies only returns early when `ctx.error !== undefined`.
- `onBefore` may return a `Response`: it answers the request, and the later middlewares and the action do not run. Any other value except `undefined` and `null` fails the request with a 500.
- `onFinish(ctx)` replaces a `res.on('finish')` listener registered in `onBefore`; `ctx.aborted` is `true` when the client went away.
- To read or change a reply, use a middleware's `onAfter(ctx)` (`ctx.response.data`, `ctx.response.statusCode`, `ctx.response.setHeader()`); to observe the reply that was sent, use the `reply` of the outcome `onAround`'s `proceed()` resolves with. Capturing the response is internal: there is no API to attach a capture to `res`.
- New: `http.routes.middlewares` mounts route middlewares on every route of the app ([Global route middlewares](../http/14-route-middlewares.md#global-route-middlewares)).
- `@Idempotent` replays a completed key of an authenticated, unrestricted principal before the policy gate, when the request has the stored fingerprint. A resend of a committed operation (a delete whose row is gone) now gets its stored reply instead of a 403 or 404 from a policy that sees the changed state. The policies do not run for that replay, and only the `'beforePolicy'` route middlewares and the server middlewares see it in `onAfter`; the `'outer'` and `'inner'` ones are not entered. Anonymous and restricted callers (a ceiling, a delegation, an impersonation, a share link, companions), keys in flight and reused keys still go through the policies first. Move a middleware that must see every replay to the `'beforePolicy'` stage ([Replays before the policies](../http/26-idempotency.md#replays-before-the-policies)).
- The idempotency key scope of a restricted principal now holds its authority (ceiling, delegation, impersonator, companions) as well as its `type:id`, on http and sockets: a scoped token, a role switch or an impersonating admin no longer gets the reply stored for the user's full session. A key such a credential completed before the upgrade runs again when it is resent.
- The `Audit` route middleware is in `@spinajs/audit-http`, not in `@spinajs/http`. It was added to `@spinajs/http` during 4.0 development and never released, so an application coming from 3.x has nothing to change. An application that followed the 4.0 branch: install `@spinajs/audit-http` and `@spinajs/audit`, import `Audit` from `@spinajs/audit-http`, move `http.audit` to `audit.http`, and replace an `AuditSink` of your own with an `AuditStore` named as the trail's `store`. A leftover `http.audit` block is not rejected: the `http` configuration accepts unknown keys at its top level, so the block is silently ignored and the middleware runs with the defaults. The events go to the `default` trail, a table of `@spinajs/audit-orm`; for the log, set `audit.trails.default.store` to `LogAuditStore`. See [Audit](../audit-http/01-audit.md).

Server middlewares:

- `before()` and `after()` are removed. A server middleware, or a `NotFoundMiddleware` or `ErrorHandlerMiddleware` replacement, that still defines either fails `HttpServer.resolve()` with an `InvalidOperation` naming the class. Use the hooks, `isEnabled()` (called once at mount, `false` mounts nothing), `resolve()` for settings and `handler()` for a third-party Express handler.
- `NotFoundMiddleware` and `ErrorHandlerMiddleware` are no longer server middlewares but the fixed tail of `HttpServer`. A replacement overrides `reply(req)` and `reply(error, req)`, which return the `Response`.
- `HttpServer` creates `req.storage` itself, as its first handler. `RequestStorage` is deprecated and no longer registered; an `Order` chosen to run after it needs no change.
- The body parsers, the cookie parser and `http.bodyLimits` are server middlewares: `JsonBodyParser`, `UrlencodedBodyParser`, `TextBodyParser` (Order 3.5), `CookieParserMiddleware` (0.5) and `BodyLimits` (3.4). `defaultMiddlewares()` holds only `helmet`. Their options move to `http.bodyParsers.{json,urlencoded,text,cookies}` (`enabled` plus the express or cookie-parser options; the cookie secret stays `http.cookie.secret`). A malformed body (400) or one over its limit (413) now carries `x-request-id` and the CORS headers, is access-logged, and is seen by the server middlewares below Order 3.5; a server middleware below 3.5 no longer sees `req.body`. A list that still holds `express.json()`, `express.urlencoded()`, `express.text()`, `cookieParser()` or `configuredCookieParser` keeps parsing with them (before every server middleware): the matching built-in is not mounted and logs one warning. The other built-ins are mounted, so a list that held only some parsers now also parses the other types and cookies: set `http.bodyParsers.<kind>.enabled: false` for the ones you do not accept. A parser wrapped in your own function is not recognised: both run, yours first. `http.bodyLimits` runs before `http.middlewares` when the list holds any handler the package did not ship, as in 3.x, and uses the `http.bodyParsers` options (your `verify` now runs on limited paths). Move the options to `http.bodyParsers` and drop the handlers. See [Body and cookie parsers](../http/01-http-server.md#body-and-cookie-parsers).
- Static files (`http.Static`) are served by the `StaticFiles` server middleware at `http.static.order`, 4.5 by default, instead of after all of them: a static request no longer runs authentication (5), `PrincipalMiddleware` (10), `AccessEpochMiddleware` (11) or a server middleware of your own above 4.5. So the `authn.http.hooks.request` refusal hook and the `Cache-Control: no-store` that authentication stamps on requests with a session no longer apply to static files. The server middlewares below `http.static.order` still run for them (CORS, request id, access log, throttle, the CSRF guard, and a maintenance or concurrency guard placed there): such a guard also answers static requests unless it lets their path through. Serving private files from `http.Static` behind your own middleware needs a higher order; `http.static.order: Infinity` restores the 3.x placement. The `http.Static` entries are now checked by the configuration schema: a misspelt key or a `Route` without a leading `/` fails the boot. See [Static files](../http/01-http-server.md#static-files).
- `compression` is no longer in `defaultMiddlewares()`. It is the `Compression` server middleware, switched off with `http.compression.enabled: false`. A `compression()` in your own `http.middlewares` list is redundant next to it.
- `x-response-time` (`ResponseTime`) and `Server-Timing` (`ServerTiming`) are set in `onAfter`: static files and replies an action wrote to `res` itself no longer get them.
- `CsrfGuard.refuse()`, `SameOriginGuard.refuse()` and `CsrfOriginGuard.refuse()` (`@spinajs/authn-http`) return the refusal `Response` instead of writing `res`.
- `http.throttle` rules and `@RateLimit` no longer send `X-RateLimit-*`; set `headers: true` to keep them. The 429 still carries `Retry-After` (see [Throttling](../http/18-throttling.md#opting-in-to-the-rate-limit-headers)). The positional `@RateLimit(limit, windowSeconds)` and a positional global floor (`options: [limit, windowSeconds]`) cannot take `headers`: switch them to the options form, `@RateLimit({ limit, windowSeconds, headers: true })` or `options: [{ limit, windowSeconds, headers: true }]`, to keep the headers.
- With `@spinajs/http-swagger`, every `@RateLimit` route now documents its 429 in the served document, and a default answer adds `components.responses.TooManyRequests`: document snapshots and generated clients change ([middleware answers](../http-swagger/07-openapi-builder.md#important-behaviour)).
- A subclass of a shipped middleware that wrapped `super.before()` overrides a hook and calls `super.onBefore(ctx)`, or overrides the decision method the middleware offers: `allowance()` (CORS), `shouldLog()` (`AccessLog`), `refuse()`, `proxyTrust()` (`RealIp`).
- Server `onBefore` and `onAround` get `ctx.route`, `ctx.controller` and `ctx.path` of the route the `RouteIndex` matches before routing ([The route before routing](../http/15-server-middlewares.md#the-route-before-routing)). Code that read `ctx.route === undefined` as "before routing" checks something else.
- `CorsMiddleware` is always mounted, so `@Cors({ origins })` routes answer without `http.cors.origins`; without either, no CORS headers are sent, as before. A subclass that overrode `isEnabled()` to return `true` for a rule-only `allowance()` no longer needs to. An overridden `allowance()` also clamps `@Cors` routes; `http.cors.allowRoutePolicies: false` ignores them.
- `CsrfGuard.controllers()` is removed: `@CsrfExempt()` is read from the mounted routes the `RouteIndex` matches. A tightening: a request is exempt only when every route that could serve it (same method and path) is `@CsrfExempt()`; 3.x exempted it when any one was. Override `isExempt(ctx, paths)` to change the decision.

Middlewares of other packages:

- `@spinajs/telemetry`: a `TelemetryMiddleware` subclass overrides `record(ctx)` instead of `onFinish(req, res)` and `routeLabel(ctx)` instead of `routeLabel(req)`; it skips a request by overriding `onBefore(ctx)` without calling `super.onBefore(ctx)` ([Customizing the request middleware](../telemetry/04-customizing-the-request-middleware.md)).
- `@spinajs/intl-http`: an `IntlHttpMiddleware` subclass that wrapped `super.before()` overrides `detectLanguage(req)` ([Request language](../intl-http/01-request-language.md)).
- `@spinajs/authz-http`: `AccessEpochMiddleware` sets `X-Access-Epoch` in `onAfter`, from the principal as it is when the reply leaves. Error replies and the 404 get it too; static files and replies an action wrote to `res` itself do not.
- `@spinajs/authn-http`: `AuthnMiddleware`, `ClientIp` and `CsrfOriginGuard` run on the hooks; a subclass overrides `onBefore(ctx)` or `refuse()` instead of wrapping `super.before()`.

## Socket command stages (`@spinajs/http-socket`)

`SocketCommandStage` is removed. Socket commands run on `SocketMiddleware`, with the hooks of http's middlewares: `onBefore(ctx)`, `onAfter(ctx)`, `onFinish(ctx)`, `onAround(ctx, proceed)`, plus `Order`, `isEnabled(handler)` and `onRegister(handler, registration)`. The migration table is in [Command pipeline](../http-socket/04-command-pipeline.md#migrating-from-socketcommandstage).

- Register with `@Injectable(SocketMiddleware)` and extend `SocketMiddleware`. `Order` and `onRegister` are unchanged.
- `execute(ctx, next)` is gone. Work before `next()` moves to `onBefore(ctx)`; a change of the result to `onAfter(ctx)` (`ctx.result`); one scope around `next()` to `onAround(ctx, proceed)`, the same body. A middleware that still defines `execute` fails the registry build with an `InvalidOperation` naming the class.
- A subclass of a built-in stage (`SizeStage`, `PoliciesStage`, ...) overrides the stage's hook instead of `execute`; the class names and `Order`s are unchanged.
- `onRegister` runs only on commands where `isEnabled(handler)` is `true`; a name check inside the hooks can move to `isEnabled`.
- New: `@UseSocketMiddleware(Type, ...options)` mounts a middleware on a socket controller or on one command.
- Idempotency still runs before the policies, unlike http: see [Idempotency before policies](../http-socket/04-command-pipeline.md#idempotency-before-policies).
- An `idempotencyKey` reused with another command or payload answers `failed_precondition` (`details.reason: 'idempotency_key_reuse'`); 3.x replayed the first command's reply. Keys stored by 3.x replay as before.

## Lint: `@spinajs/authz/require-accessible`

The rule exempts only queries inside `runAs(SYSTEM, reason)`. A query inside `runAs(user, ...)` is now reported, as the run-time guard always refused it: add `.accessible(permission)`, or `.unscoped(reason)` for a deliberate read of every row. There is no option that brings the 3.x exemption back.

## Scope attribute key (`@spinajs/authz-orm`)

`authz_scope_attribute` has one primary key column, `id`, instead of `(scope_type, scope_id, path)`, so the ORM write capture and row history can follow it. The three columns stay unique together (index `authz_scope_attribute_leaf`). The migration `AuthzScopeAttributeKey_2026_11_25_00_00_00` rebuilds the table: it creates the new shape beside the old one, copies every row with its `id`, drops the old table and renames the new one.

Run `npx spinajs migrate-up` once before the new version boots, with every process of the old version stopped. The migration does not hold writers off, but it notices them: when an attribute was written while it copied the rows, it stops before it drops the old table with `authz_scope_attribute changed while it was copied: stop every writer, then run npx spinajs migrate-resolve --name AuthzScopeAttributeKey_2026_11_25_00_00_00 --rolled-back and npx spinajs migrate-up`. Do exactly that; nothing was lost. The check waits for a write whose transaction is still open when the copy ends, so that one is caught too. Only a write that starts after the check and commits before the drop, a moment of two statements, is still lost without a word. On SQLite a writer that keeps its transaction open longer than the driver's retries makes the run fail with the database's busy error instead; the old table is whole then as well, and the same two commands apply. After the rebuild an old process can still read and delete attributes, but its inserts carry no `id` and the table refuses them (a MySQL server without strict mode stores `''` instead, once). With the ORM's migration check on (the default) the new version refuses to boot until the migration ran.

On MySQL the rebuilt table compares `id`, `scope_type`, `scope_id` and `path` case- and accent-sensitively (`utf8mb4_0900_bin`; `utf8mb4_bin` on servers without it, MySQL 5.7 and MariaDB, which still ignores trailing blanks), as PostgreSQL and SQLite always did. Before, the server's default collation made `org:O1` read and replace the attributes of `org:o1` (and of `org:ö1`). An application that wrote a scope with one spelling and reads it with another gets no attributes for the second spelling after the upgrade: write and read each scope with one spelling. To find scopes whose attributes no reader will find, compare the stored scope ids with the ids of the resources of that type exactly; a stored id without an exact match is written with another spelling than the resource has (or its resource is gone). On MySQL 8, for scope type `org` kept in table `org`:

```sql
SELECT a.scope_type, a.scope_id, a.path FROM authz_scope_attribute a
WHERE a.scope_type = 'org'
  AND NOT EXISTS (SELECT 1 FROM org r WHERE r.id COLLATE utf8mb4_0900_bin = a.scope_id COLLATE utf8mb4_0900_bin);
```

`DbScopeAttributeStore` now refuses a scope type, scope id or path that is not well-formed UTF-16 (a lone surrogate) with `AuthzConfigError`, before any SQL: every driver stored such text as U+FFFD, so two different ids shared one scope.

If the run stops half-way, the rebuild can always be finished by running the migration again; no state in between loses rows. When the process was killed, run `npx spinajs migrate-up` again. When the migration threw, it is recorded as failed and blocks `migrate-up`: run `npx spinajs migrate-resolve --name AuthzScopeAttributeKey_2026_11_25_00_00_00 --rolled-back`, then `npx spinajs migrate-up`. Do not resolve it with `--applied`: the table may be half-way, with its rows in `authz_scope_attribute_rebuilt`.

`npx spinajs migrate-down --name AuthzScopeAttributeKey_2026_11_25_00_00_00` restores the three-column key with every row. Run it with the new version, before the old one starts again: a bare `migrate-down` rolls back the whole last batch, and the old version does not have the migration class. On MySQL it fails with a duplicate-key error, before it drops anything, when two leaves were written after the upgrade that the 3.x key folds into one (`O1` and `o1`); delete one of each pair first. To list them on MySQL 8 (use the database's default collation in place of `utf8mb4_0900_ai_ci`):

```sql
SELECT scope_type COLLATE utf8mb4_0900_ai_ci AS t, scope_id COLLATE utf8mb4_0900_ai_ci AS i, path COLLATE utf8mb4_0900_ai_ci AS p,
       GROUP_CONCAT(CONCAT('[', scope_id, ']')) AS spellings
FROM authz_scope_attribute GROUP BY t, i, p HAVING COUNT(*) > 1;
```

PostgreSQL and SQLite never fold two leaves into one, so there `migrate-down` has nothing to refuse.

Code that reads and writes attributes through `DbScopeAttributeStore` or `AuthzAdmin` changes nothing. Code that inserts rows into the table itself supplies `id` with `scopeAttributeId(scope_type, scope_id, path)` (`scope_id` is `''` for `$global`); code that used `ScopeAttributeRecord` by its three-column key uses `id`, or a `where` on the three columns. `ScopeAttributeFields` gains `id`.

## Queue jobs that run as `SYSTEM` (`@spinajs/authz-queue`)

A job with `@Job({ runAs: 'system' })` and no `access` must say why it runs as `SYSTEM`: put `@SystemTask('<reason>')` from `@spinajs/queue` on the job class, or declare `@Job({ runAs: 'system', access: [...] })`. Without either the handler does not run: the hook throws `JobWithoutSystemTask` (`system_task_missing`), a permanent failure: the job is marked `dead` at once, and amqp and stomp dead-letter it without a retry. SQS leaves the message for redelivery, and the next delivery finds the `dead` row and is acknowledged without running, unless `queue.deduplicate` is `false`: then each redelivery is refused until the queue's redrive policy or its retention period ends it. This holds for messages emitted by 3.x and consumed by 4.0. `spinajs doctor` lists such jobs as `AUTHZ004`. `authz.queue.systemTask: 'warn'` lets them run with one warning per job class while you add the decorators.

## From 3.0.24 to 3.0.29

4.0 carries the breaking changes of the late 3.x releases.

- **The application never migrates.** `Orm.resolve()` applies no migration and runs no `data()` seed. It reads the tracking tables through `OrmMigrationGuard` and fails with `PendingMigrationsException` while a migration is pending or failed (`db.MigrationCheck`, default `'fail'`; `'warn'` logs and boots, `'off'` reads nothing; `Migration.Check` sets it per connection). A configuration that still sets `Migration.OnStartup`, `true` or `false`, fails the boot. `Orm.Migrator`, `orm.Migrator.ready()`, `IOrmMigratorOptions`, `MigrateOnStartup` and `AwaitsStartupMigration` are removed, and `DI.resolve(OrmMigrator)` throws. An application that migrated at boot runs `npx spinajs migrate-up` as a deploy step instead; it applies the migrations and their seeds under one lock per connection, and with a manifest in effect it applies the migrations the manifest lists. A process that has to migrate itself (a desktop app, a single instance with no deploy step) calls the migration tool before anything resolves the `Orm`. Tests call `migrateTestDatabase(container)` from `@spinajs/orm/testing`, or `migrate(container)` of a `@spinajs/testing-orm` database ([Deploying migrations](../orm/10-migrations.md#deploying-migrations)).

  ```ts
  // 3.0.26: the boot applied the migrations of OnStartup connections
  db: { Connections: [{ Name: 'main', Driver: 'orm-driver-mysql', Migration: { OnStartup: true } }] }
  const orm = await DI.resolve(Orm);
  await orm.Migrator.ready();

  // 4.0: `npx spinajs migrate-up` ran in the deploy step; the boot only checks
  db: { Connections: [{ Name: 'main', Driver: 'orm-driver-mysql' }] }
  const orm = await DI.resolve(Orm);

  // 4.0, a process that migrates itself, before anything resolves the Orm
  const migrator = await resolveMigrationTool();
  await migrator.migrate();
  const orm = migrator.Orm;
  ```
- **Only `authz.models` activates authorization models**, by class name, and `authz.domains.<name>.models` per domain. `registerRbac`, `buildRbac`, `useRbac` and `authz.use` are removed. Root without `authz.models` has no model, so every check denies. `authz.models` is a config value, not a composed array: an environment file that sets it replaces the list ([Registering the shipped models](../authz/04-host-boot-and-configuration.md#registering-the-shipped-models)).

## MySQL connections without `TimeZone`

4.0 keeps UTC. A MySQL connection without `TimeZone` pins its sessions to UTC (`SET time_zone = '+00:00'`), stores datetimes as the UTC wall clock and uses `UTC_TIMESTAMP(3)` for `driver.now()` and `driver.ago()`, as every 3.x release did (3.0.0 to 3.0.29). `TimeZone: 'SYSTEM'` is opt-in ([MySQL driver](../orm-mysql/01-mysql-driver.md#dates-and-time-zone)).

- **Coming from 3.x:** nothing to do. No row moves and nothing is converted, in any process zone.
- **Coming straight from 2.x**, without 3.0's upgrade step (its release notes, item 9): 2.x stored the wall clock of the process that wrote each row. Either set `TimeZone: 'SYSTEM'` on the connection and keep every node process and the MySQL server in one zone, or convert the rows to UTC once, before the first 4.0 start:
  1. Back up the database. The conversion cannot be undone, and running it twice shifts the rows twice. Stop every writer, and record that it ran (eg. as a migration).
  2. Convert only rows written by processes that all ran in one zone. Never convert rows written by 3.x, which are already UTC, and never a table written by processes in several zones: its rows cannot be told apart.
  3. Check that the server knows the zone: `SELECT CONVERT_TZ('2030-01-15 12:00:00', 'Europe/Warsaw', '+00:00')` must return `2030-01-15 11:00:00`. For a zone it does not know, for example when its time zone tables are not loaded, it returns `NULL`, and the `UPDATE` below would write `NULL` into every value of a nullable column.
  4. Convert every datetime column of a table in one `UPDATE`. A second `UPDATE` of the same rows stamps an `ON UPDATE CURRENT_TIMESTAMP` column with the current time. `UPDATE` triggers fire.

  ```sql
  UPDATE my_table SET created_at = CONVERT_TZ(created_at, 'Europe/Warsaw', '+00:00'), updated_at = CONVERT_TZ(updated_at, 'Europe/Warsaw', '+00:00');
  ```

  - Use the named zone. A fixed offset such as `'+01:00'` is wrong for the half of the year in daylight saving time.
  - The hour a zone repeats when daylight saving time ends was stored as the same wall clock twice. Nothing recovers which instant such a row meant, so values from that hour may be one hour off.
  - `TIMESTAMP` columns, views, events and hand-written SQL are not covered by this statement; check them separately (not run).
- **Coming from a 4.0 pre-release** (a `v4` build, or the unpublished master 3.0.30) that ran without `TimeZone`: that build stored datetimes as `SYSTEM` does, the wall clock of the node process, and kept the server's session zone.
  - **To keep exactly what it did, set `TimeZone: 'SYSTEM'`** on the connection, with every node process and the MySQL server in one zone.
  - Under the new default, rows it wrote in a process outside UTC read shifted by that process's offset: a row written in `Europe/Warsaw` for `2030-01-15T12:00:00Z` holds `2030-01-15 13:00:00.000` and now reads as `13:00Z`. If every datetime in the database was written that way, by processes in one zone, you may convert them to UTC once with the steps above, and then leave `TimeZone` unset.
  - If the same columns also hold rows 3.x wrote (UTC), the table cannot be converted mechanically: nothing in a row says which way it was written. Under the new default the pre-release rows read shifted; under `TimeZone: 'SYSTEM'` the 3.x rows do. Repair it from a backup or from what the application knows about each row.
  - A pre-release whose node processes AND MySQL server all ran in UTC wrote UTC, and nothing needs doing. With a server in another zone, `TIMESTAMP` columns and values the server stamped (`DEFAULT CURRENT_TIMESTAMP(3)`, `ON UPDATE`, `NOW()` in SQL) hold the server's zone and read shifted under the new default (checked on MySQL 8.4 with a session in `Europe/Warsaw`: a `TIMESTAMP` written for `12:00Z` reads `11:00Z`).

## Removed: `@spinajs/queue-orm-transport`

The package is removed from the monorepo and is no longer published. The database-backed queue transport is not available in 4.0. Use another transport (for example `@spinajs/queue-stomp-transport`) or stay on 3.x if you depend on it.

## Removed: `@spinajs/tasks`

The package is removed from the monorepo, with `@Task()`, `runTask`, `TaskSuccess`, `TaskFailed`, the `__task` / `__task_history` models and the `tasks.*` configuration. Recurring and on-demand work is a `@Schedule` class of `@spinajs/scheduler`; its runs are recorded in `__scheduler_run` with attempts, steps, errors and retries. The scheduler migration runs on the `default` connection.

**A `@Task` method becomes a `@Schedule` class.** Move the method body into `execute(ctx)`, or into a function that `execute` and the callers share. A task that only ran when called is a `manual` schedule. Where the code called the decorated method, call `SchedulerService.runInline()`, which runs the function now, in the calling process, as a `manual` run of the schedule:

```ts
// 3.x
@Task('send-digest', 'Sends the daily digest')
public async sendDigest() { /* ... */ }
```

```ts sample
import { DI } from '@spinajs/di';
import { RunContext, Schedule, ScheduledTask, SchedulerService } from '@spinajs/scheduler';

async function sendDigest(_ctx: RunContext): Promise<number> {
  return 0;
}

@Schedule('send-digest', { manual: true })
export class SendDigest extends ScheduledTask {
  public execute(ctx: RunContext): Promise<number> {
    return sendDigest(ctx);
  }
}

export async function sendDigestNow(): Promise<number> {
  const scheduler = await DI.resolve(SchedulerService);
  return scheduler.runInline('send-digest', (ctx) => sendDigest(ctx));
}
```

What a caller sees changes:

- The function's error rejects the call. A `@Task` method resolved `{ error: true, message }`.
- A call while another run holds the schedule lease throws `ScheduleOverlap` (a `RunConflict`). A `taskStacking: false` method resolved `undefined` with a warning.
- `taskStacking: true` has no equivalent: inline calls of one schedule never run side by side. Call the function directly when concurrent calls must not exclude each other, at the cost of the run record.
- `lockTtl` is gone; the run lease lives `scheduler.leaseTtl`. Runs no longer take the `@spinajs/threading` mutex, so a `Mutex` registered only for tasks can be removed.
- A cancel, a timeout (the schedule's `timeout`) or a lost lease rejects with `RunAbortedError`. See [Inline runs](../scheduler/README.md#inline-runs).

**`TaskSuccess` and `TaskFailed` are gone.** Every run, an inline one included, sends the scheduler's events instead: `ScheduleRunSucceeded` (`Schedule`, `RunId`, `Attempt`, `DurationMs`) and `ScheduleRunFailed` (`Schedule`, `RunId`, `Attempt`, `Status`, and `Error`, a structured error with `name` and `message` in place of `Reason`). `ScheduleRunFailed` is sent for a run that ends `failed`, `dead` or aborted by its timeout; a cancel, a shutdown or a lost lease sends no event. Both are routed to the black-hole connection `scheduler-empty-queue` by default; route them with `queue.routing.ScheduleRunSucceeded` and `queue.routing.ScheduleRunFailed`, and delete the `TaskSuccess` / `TaskFailed` routing and the `task-empty-queue` connection from your configuration.

**A `scheduler.schedules` entry can no longer name a `@Task` method.** `task` names a `@Schedule` class by its class name. An entry such as `{ name: 'digest', task: 'send-digest', cron: '0 8 * * *' }` now fails the boot with `ScheduleValidationError` (`unknown task 'send-digest' (no @Schedule class with this name)`). Point it at the class (`task: 'SendDigest'`), or drop `task` and give the entry the schedule's name to change that schedule's timing.

**Tables and the event that 3.x left in the database.** The `Task_2024_12_03_11_41_00` migration created `__tasks` and `__task_history` on the `default` connection and, on MySQL, the event `__task_delete_old_entries`, which keeps deleting `__task_history` rows every day. 4.0 ships no migration that drops them. Once the history is no longer needed, drop them by hand, the event first, and delete the migration's row from the tracking table (`Migration.Table`, default `spinajs_migration`), which the migrator otherwise reports as an orphan on every run:

```sql
-- MySQL
DROP EVENT IF EXISTS `__task_delete_old_entries`;
DROP TABLE IF EXISTS `__task_history`;
DROP TABLE IF EXISTS `__tasks`;
DELETE FROM `spinajs_migration` WHERE `Migration` = 'Task_2024_12_03_11_41_00';

-- PostgreSQL, SQLite, SQL Server
DROP TABLE IF EXISTS "__task_history";
DROP TABLE IF EXISTS "__tasks";
DELETE FROM "spinajs_migration" WHERE "Migration" = 'Task_2024_12_03_11_41_00';
```

## Removed: the `authn_audit` table of `@spinajs/authn-orm`

`DbAuthnAuditSink`, the `AuthnAudit` model, `AuthnAuditRetention`, the `authn:audit-purge` command and the keys `authn.audit.retentionDays` and `authn.audit.purgeInterval` are removed; the two keys are refused at boot. export default {

```sql
-- MySQL

-- PostgreSQL, SQLite, SQL Server
```

The migration's row in the tracking table stays: the migration still exists and still owns the other `authn_*` tables. // 3.x

```ts
// 4.0
import { skipsAuthInDevelopment } from '@spinajs/authz-http';
```

A subclass of `TelemetryAccessPolicy` inherits the protected `read()` and `guard` from [`SlotAccessPolicy`](../authz-http/12-slot-access-policy.md); the guard of an `'AccessPolicy'` slot holds `permissions` and `domain` where it held `holder`.

## Teams and tenancy (`@spinajs/teams`)

An app that imports `@spinajs/tenancy` and uses `@spinajs/teams` must set `teams.tenancy`, or its authz domain refuses
to boot: an HTTP app when the server starts listening, a worker or a CLI at the first team operation the authz service
checks. In this release set it to `false`:

```json
{ "teams": { "tenancy": false } }
```

`false` keeps teams global, as before the upgrade: a team can hold users of several tenants, and a team id of one
tenant is found from another. `true` (teams inside tenants) comes with `@spinajs/tenancy-orm/teams` in a later release
and refuses the boot until then. See [Teams and tenancy](../teams/README.md#teams-and-tenancy).

## DI

- `asValue` / `asMapValue` bindings are registrations. `clearCache()` keeps them; `clearRegistry()` and `clear()` drop them. Bootstrappers that re-registered a value after `clearCache()` can be deleted.
- `register(X).as(Y, { replace: true })` makes a re-registered class the last (winning) registration; without the option the first position is kept, as before.
- `DI.child({ isolateSingletons: true })` creates a child that owns every singleton it resolves. `container.snapshot()` / `container.restore(snapshot)` capture and put back registrations, values, cached instances and listeners.
- `restore()` disposes the services created since the snapshot against the live state, then swaps the snapshot back. When resolutions keep starting while it disposes (a poller, a reconnect loop), the state is still put back and `restore()` rejects with `RestoreIncomplete`, which names what was still resolving.

## `typescript` and `glob` are optional peers

`@spinajs/http` no longer installs `typescript`, and `@spinajs/reflection` no longer installs `typescript` or `glob`. Both are optional peer dependencies, so `npm install` does not bring them in.

**`typescript` (`@spinajs/http`).** Route parameter names come from the manifest when one is in effect (`system.manifest.mode` `prefer` or `require`), else from the TypeScript controller cache. The cache imports `typescript` only to parse a controller it has no entry for. An app in `off` mode (the default) does one of these:

- installs `typescript` as a dependency of the app (a `devDependency` is not enough when the production install omits dev dependencies);
- builds the controller cache ahead of time with `spinajs http:controllers:cache` (for example in the image build, where `typescript` is present) and ships the `__fs_controller_cache__` directory: a boot whose entries all exist never loads the compiler;
- switches to the manifest: `spinajs build`, then `system.manifest.mode` `prefer` or `require`.

Without any of them, the first controller the cache has to parse fails the boot with `NoControllerMetadata`, which names the optional peer and these three ways out.

**`glob` (`@spinajs/reflection`).** `@ResolveFromFiles` and `@ListFromFiles` import `glob` on the first directory scan. An app that scans directories (`off` mode, or a `prefer` mode section the manifest does not cover) installs `glob` `^8`, or lists from the manifest. Without it the first scan fails with `ReflectionException`, naming the optional peer. Today `@spinajs/configuration` (and `@spinajs/intl`, `@spinajs/orm`, `@spinajs/validation`) still depend on `glob`, so a usual npm install resolves it anyway; do not rely on that, it is not a guarantee under strict layouts such as pnpm.

**`typescript` (`@spinajs/reflection/typescript`).** `TypescriptCompiler` needs `typescript` installed next to `@spinajs/reflection`.

Other changes in the same area:

- `DefaultControllerCache` moved off the package root: `import { DefaultControllerCache } from '@spinajs/http/cache'`. The documentation types (`IMethodDoc`, `IControllerDocumentation`, ...), `parseFnParamNames` and `isOnDiskSource` stay on the root.
- In `require` mode a controller with a source file that the manifest does not list fails registration with `NoControllerMetadata`. Rebuild the manifest after adding a controller.
- `spinajs build` no longer loads an app class that discovery would not load. A controller outside `system.dirs.controllers` was mounted in `prefer` and `require` and is not any more, unless something registers it; the same goes for socket controllers, schedules, commands and migrations. Each is reported as a `CMP006` warning: declare its folder in `system.dirs` or move it. A build where no configured dir maps into the app now fails with `CMP007`; `--allow-no-dirs` builds a deliberate no-dirs app. Build with the `APP_ENV`, `--app`, `--apppath` and `--config-path` of the deployment, because the manifest reflects that config. See [The app's own classes](../manifest/README.md#the-apps-own-classes).
- **Rebuild the manifest after upgrading.** A manifest built before `mountedBy` existed has no such flags, so it keeps mounting every class it lists until `spinajs build` runs again. `MANIFEST_VERSION` stays 2 because the field is additive; nothing refuses the old file.
- A manifest built with `spinajs build --no-schemas` has no payload schemas for the app's socket contracts. Such an app used to run its contracts unvalidated without a word. Now a `require` boot fails and names the contracts, and `prefer` logs one warning naming them. Build without `--no-schemas` when the app binds socket contracts.
- A controller's manifest entry now lists the routes it inherits from base classes of its package, with the subclass's path and generic types. After rebuilding, request validation of an inherited generic route uses the DTO the subclass binds: `POST /articles/create` on `ArticlesController extends BaseCrud<ArticleDto, CreateArticleDto>` is validated against `CreateArticleDto`. This fixes a bug: the old schema came from the unbound type parameter and rejected every non-empty body with a 400, so valid requests now pass and requests that do not match the DTO (including `{}`) get a 400. A subclass without its own `@BasePath` is recorded at the base path it inherits, so the first `spinajs manifest:diff` against an older manifest shows its routes at corrected paths and the inherited routes as added. The report warns when base and head come from different compilers: rebuild the base with the new compiler to compare like with like. `spinajs doctor` now checks inherited routes too, so a subclass of a guard-less base such as `UploadController` without `@Access`, `@Policy`, `@AllowAnonymous` or `@Public` fails HTTP002.
- `TypescriptCompiler` moved to `import { TypescriptCompiler } from '@spinajs/reflection/typescript'`. Importing `@spinajs/reflection` loads neither `typescript` nor `glob`; `glob` is imported on the first directory scan.

## CLI

- `spinajs` run where no application is found fails with `error: no application found in <dir>` and a non-zero exit code when it is given a command. It used to exit 0 having done nothing, so a script that ran `spinajs migrate up` from the wrong directory passed. Run it from the application directory.

## Tests

`@spinajs/testing` replaces per-package `TestConfiguration` registration and `test/support/config-boot.ts` copies: `createTestApp`, `useTestApp`, `configurationViolations`, `readingFrom`, `fakeContainer`, `setPastSchema`, `disposeTestApps`.

- Only one root app can be live at a time, and the slot is claimed before the boot starts: a second root `createTestApp` rejects at once, naming the holder. Use `scope: 'child'` for apps side by side.
- A root boot that does not finish within `bootTimeout` (default 30000 ms; `useTestApp` uses 90% of the hook timeout; `0` or `Infinity` disables it) is abandoned and root is restored, so the next suite boots cleanly.
- `dispose()` restores root and rejects with `RestoreIncomplete` when a service keeps resolving while it is disposed.

## Adopting the 4.x tooling

None of this is required to run on 4.0, and none of it is done by the codemod. Do it after the app boots on 4.0, in this order:

1. **Build a manifest.** Compile, then `spinajs build`, and read what it reports ([What is new in 4.x](../whats-new-4.0.md#from-build-to-a-running-app), [`build`](../cli/08-command-reference.md#build)). Start with `system.manifest.mode` `off` or `prefer`.
2. **Run `spinajs doctor`** and fix its errors ([spinajs doctor](../compiler/doctor.md)). Rule `HTTP002` reports a route with no `@Access`, `@Policy`, `@AllowAnonymous` or `@Public` on it or its class. A route that is open on purpose (a login, a health check, a webhook) takes `@Public('reason')`, which only records the intent and changes nothing at request time ([`@Public(reason)`](../http/13-policies.md#publicreason-a-route-that-is-open-on-purpose)). `@Public` next to a guard on the same route is reported as `HTTP006`.
3. **Add the manifest to CI** with a generator drift check and, if you want it, the PR comment from `manifest:diff` ([Manifest diff and CI](../manifest/diff-and-ci.md)).
4. **Switch to `require`** where the app is deployed, and ship the manifest with it ([Deploying a manifest-built app](../manifest/deploying.md)). Check the list in [What changes when you switch manifest mode on](../manifest/README.md#what-changes-when-you-switch-manifest-mode-on) first: request arguments are validated against derived schemas and query values are coerced.
5. **Replace hand-written `@Schema` duplicates** of your DTO types with [JSDoc constraint tags](../validation/09-dto-constraints-jsdoc.md) where they only repeated the TypeScript type.
6. **Generate a client** instead of writing one by hand ([`@spinajs/client`](../client/README.md)), and the OpenAPI or AsyncAPI document ([`@spinajs/openapi`](../openapi/README.md), [`@spinajs/asyncapi`](../asyncapi/README.md)).
7. **Move your tests** to `@spinajs/testing` ([Testing](../testing/README.md)).
8. **Type your DI keys** that have no class with `token<T>(key)` ([Typed tokens](../di/16-typed-tokens.md)).

## Release process

Releases are moving to [changesets](https://github.com/changesets/changesets) with one fixed group, `@spinajs/*`: every package gets the same version, bumped by the highest change level in the release. Automated releases are not enabled yet; the existing release scripts (`scripts/bump-all.mjs`, `scripts/publish-all.mjs`) and workflow are still in use until they are.

Once enabled, the intended flow is:

- Every pull request that changes behaviour adds a `.changeset/*.md` entry (`npx changeset`).
- A scheduled run (or a manual trigger) opens a "version packages" pull request that bumps versions, writes the changelogs and updates the lockfile.
- Merging that pull request publishes to npm and tags the release.
