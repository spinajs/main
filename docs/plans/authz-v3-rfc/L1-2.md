# L1-2 native:rbac.assignment in kit worlds, and type-only `under` scopes

Status: proposed by L1 (task 10). Asks the kit owner (and F3 for point 2). L1 is not blocked: the
model lists scoped assignments with core `under` by default, and emits `native:rbac.assignment` only
through the opt-in `rbacAssignmentExtension`.

Point 1 APPROVED and APPLIED 2026-10-04 (K4), as a variant of the first proposal: in a world with
`rbac`, `instantiateWorld` gives every adapter whose spec leaves `compiles` out the core ops plus
`'native:rbac.assignment'` and `'native:rbac.threshold'` (both in `RBAC_RESIDUALS`; an extra
`compiles` entry never causes a refusal). One rule covers every RBAC world, today's (B05.rbac,
B06.rbac, B15.rbac, B16.rbac, B17.rbac) and the rule parts L1b and L4b add (B05.sql rule 11 among
them), with no edit per world; an explicit `compiles` (the rule 4 cases) is kept. The second
proposal would need FakeAdapter to see the host's NativeFilter registry, which it does not;
FakeAdapter already evaluates any native op whose filter the context holds. B06's `fileAdapter`
now leaves `compiles` out unless given.
`authz-rbac/test/behaviour.native.test.ts` runs every RBAC part L1 owns with
`rbacAssignmentExtension`. Point 2 (type-only `under` scopes) stays open for F3 and the kit owner.

## 1. RBAC worlds whose adapters do not compile the native op

Design §6.1.2 says a type-level RBAC vote lists scoped assignments with `native:rbac.assignment`,
and the B06.rbac note expects it ("the harness's list runs the residual with the model's
NativeFilter"). But every RBAC world that has an adapter uses `FakeAdapter`'s default
`compiles: CORE_FILTER_OPS`:

- B06.rbac (`fileAdapter()`);
- B15.rbac;
- B16.rbac;
- B17 lanes;
- the B05.rbac rule 8 and rule 11 worlds.

A list-scoped adapter that does not compile an op the model declares fails boot rule 4. Measured
on this branch: with the op declared, B06.rbac and B16.rbac fail at boot with
`[6.5/4] … residual ops "native:rbac.assignment" are not compiled by adapter "fake"`.

L1 therefore leaves the op out of the model's capabilities by default. Type-level votes use `under`
over the scopes of the principal's live scoped assignments. That is the same set of rows, from the
gathered snapshot, and the kit's B06.rbac part passes check ⇔ filter. `rbacAssignmentExtension`
declares the op, registers `RbacAssignmentFilter`, and switches the vote to the native term. A
lane-local part, `B06.rbac-native`, runs the B06.rbac data with an adapter that compiles the op.

**Proposal:**

- When L1b or L4b need the native op in kit worlds, which they will for the rule parts (§12.4) that
  `under` cannot carry, the kit adds `RBAC_ASSIGNMENT_OP` (the string
  `'native:rbac.assignment'`) to the `compiles` of the adapters of those RBAC worlds.
- Or the kit gives `FakeAdapter` a way to declare that it evaluates every op that has a registered
  NativeFilter in memory.

Until then, production wiring enables `rbacAssignmentExtension` for the types that `authz-orm`
compiles. Its `types` option limits the native term to those types, while the others keep
`under`. The declaration itself cannot be per type, because `capabilities.residuals` is
model-wide and boot rule 4 reads it for every route. So a domain that routes RBAC to any
list-scoped type whose adapter lacks the op must leave the extension off, or the kit and engine
need a per-type declaration.

## 2. Type-only scopes in `under`: engine and kit disagree

`under` with a scope that has no id is read in two ways:

- the engine (`engine/evaluate.ts` `under`): "some ancestor has this type";
- the kit (`filter-eval.ts` `under`): `sameRef`, so only an ancestor that is itself type-only
  matches.

A fast-check property in L1 found it: `under [{ type: 'project' }]` selected no file rows in the
kit, while the engine and the check path said yes.

L1 now never puts a type-only scope in a row filter. A type-only assignment scope `{ type: T }`
applies to resources of type T only, on checks and lists alike. **Proposal:** F3 and the kit owner
pick one meaning for a type-only `under` scope, and align `evaluateFilter` with the engine (or the
contract comment with the kit).
