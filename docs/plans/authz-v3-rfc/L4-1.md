# L4-1: a B20 case for the JOIN ON placement of `relationScope: 'join'`

Status: applied by K4 (e8911c196, `test(authz-testing): add the B20 JOIN ON cases (RFC L4-1)`);
L4 task 11 runs the cases in B20.orm on SQLite and Postgres. Proposed by L4 task 7; owner of the
change: F5 (`@spinajs/authz-testing`).

## Problem

B20 says a residual of a type with `relationScope: 'join'` goes into the JOIN ON. The kit has
no case for it: its B20 note says the design does not fix the shape of a query that joins
the scoped model, and that L4 proposes the case by RFC. `OrmQuery` has no query that joins
another model, `OrmModelSpec` has no belongsTo relation, and `OrmResult` cannot report what
a join returned. B21's `related` op covers a many-to-many read, not a join.

L4 implements the placement (task 6) and tests it in its own suite (task 7, on SQLite and
Postgres): a belongsTo target populated into a query puts its residual into the LEFT JOIN
ON, so the parent rows stay and the target columns are NULL where the principal may not
read the target.

## Change (kit, `packages/authz-testing/src/behaviour/lane.ts` and B20)

1. `OrmModelSpec` gains

   ```ts
   /** `@BelongsTo(target, column, 'id')` on the property `name`. */
   readonly belongsTo?: readonly { readonly name: string; readonly target: string; readonly column: string }[];
   ```

2. The `select` member of `OrmQuery` gains `readonly populate?: string`: the name of a
   `belongsTo` relation of the model, populated into the query.
3. `OrmResult` gains `readonly populated?: Readonly<Record<string, string | null>>`: per row
   id the query returned, the id of the populated target, `null` when the join found none.
4. `OrmExpectation` gains `readonly populated?: Readonly<Record<string, string | null>>`,
   compared with `deepEqual`. The existing `where` flag tells the two placements apart: with
   `'join'` the executed SELECT has no WHERE.

## Cases (B20, part `orm`)

`TASK` as in B20 (alice owns t1 and t3, bob owns t2) and

```ts
const NOTE: OrmModelSpec = {
  name: 'Note',
  columns: ['task_id'],
  rows: [
    { id: 'n1', task_id: 't1' },
    { id: 'n2', task_id: 't2' },
    { id: 'n3', task_id: 't3' },
  ],
  belongsTo: [{ name: 'task', target: 'Task', column: 'task_id' }],
};
const JOINED_TASK: OrmModelSpec = { ...TASK, relationScope: 'join' };
const populated = { op: 'select', model: 'Note', populate: 'task' } as const;
```

| Case | World | Step | Expected |
|---|---|---|---|
| select: a `relationScope: 'join'` target's residual goes into the JOIN ON; the parent rows stay | `ormWorld({ 'task:read': OWNER }, [JOINED_TASK, NOTE])` | `as('bob', orm(populated, …))` | `{ ids: ['n1', 'n2', 'n3'], populated: { n1: null, n2: 't2', n3: null }, where: false }` |
| select: a `relationScope: 'where'` target's residual goes into the WHERE; parent rows whose target is hidden drop | `ormWorld({ 'task:read': OWNER }, [TASK, NOTE])` | `as('bob', orm(populated, …))` | `{ ids: ['n2'], populated: { n2: 't2' }, where: true }` |
| select: a populated target with no permit at all is AccessDenied (H16) | `ormWorld({}, [JOINED_TASK, NOTE])` | `as('bob', orm(populated, …))` | `{ throws: 'AccessDenied' }` |

`Note` has no `type`, so it is not scoped; only the populated `Task` is.

The SQL L4 executes for the first case (table names as the harness generates them):

```sql
-- SQLite
SELECT … FROM `note` as `$Note$` LEFT JOIN `task` as `$task$`
  ON `$Note$`.task_id = `$task$`.id
  AND ((typeof(`$task$`.`id`) = 'text' AND (typeof(`$task$`.`owner`) = 'text' AND `$task$`.`owner` = ? COLLATE BINARY)))
-- bindings ['bob']

-- Postgres
SELECT … FROM "note" as "$Note$" LEFT JOIN "test"."task" as "$task$"
  ON "$Note$".task_id = "$task$".id
  AND (("$task$"."id" IS NOT NULL AND ("$task$"."owner" IS NOT NULL AND "$task$"."owner" = CAST(? AS text) COLLATE "C")))
-- bindings ['bob']
```

The cases check rows and the absence of a WHERE, not this text, so a harness may alias or
qualify tables its own way.

## Harness (L4 task 11)

`ormHarness` runs `populate` as `Model.query().populate(name)` and reads `populated` from the
hydrated rows (`row[name].Value?.id ?? null`). Two notes for the `related` op of B21, which
the harness implements in the same task: it must read through `Model.where(pk).populate(relation)`
or the relation object's `populate()`. The static `Model.populate(relation, id)` joins the
target table directly and is refused (`Forbidden`) for a scoped target.
