## (a) Re-export `FsDecorator` from `@spinajs/fs`

### Problem

`packages/authz-fs/src/api.ts` holds a mirror of `FsDecorator`, written before L7 task 1 added the class to
`@spinajs/fs` (commit "feat(fs): add the FsDecorator hook and signedUrl"). The barrel exports the mirror.
fsService resolves `Array.ofType(FsDecorator)`
with the `@spinajs/fs` class, so a decorator an app writes against the class it imports from
`@spinajs/authz-fs` (`@Injectable(FsDecorator)`) is registered under another token and silently never
applied. `AuthzFsDecorator` already extends the `@spinajs/fs` class.

### Change

```ts
// packages/authz-fs/src/api.ts
export { FsDecorator } from '@spinajs/fs';
```

The mirror and its comment go. The shape is the same (`order`, `decorate(instance, config)`), so the pinned
shape in `test/api.test.ts` holds; the authz-fs API snapshot changes from a class to a re-export.

## (b) B02.adapter

The kit declares the part with `facets: ['fs']` and no cases. The cases need the `boot` facet too (the boot
must fail), so the part becomes `facets: ['boot', 'fs']`. Data, as run by L7 (`test/proposed/B02-adapter.ts`):

```ts
const alice = userPrincipal('alice');

/** uploads holds a.txt and has a `compact` method no operation table maps; m1 permits alice everything. */
const fsWorld = (fs: Readonly<Record<string, unknown>>, permissions: World['permissions'] = []): World => ({
  permissions,
  principals: { alice },
  combine: combine('deny-overrides', 'm1'),
  models: [staticModel('m1', { votes: (req) => (req.principal.id === 'alice' ? permit() : {}) })],
  config: { fs },
  lane: { fs: { providers: [{ name: 'uploads', files: { 'a.txt': 'A' }, extraMethods: ['compact'] }] } },
});

const unregistered = (mode: string) => ({ uploads: { mode, operations: { compact: 'fs:compact' } } });

const cases: Case[] = [
  {
    name: 'enforce: an operation mapped to an unregistered permission fails the boot of the domain that checks the filesystem',
    world: fsWorld(unregistered('enforce')),
    boot: { throws: 'AuthzConfigError', message: ['$domain', 'fs:compact', 'authz.fs.uploads.operations.compact'] },
    steps: [],
  },
  {
    name: 'audit: the same mapping fails the boot too',
    world: fsWorld(unregistered('audit')),
    boot: { throws: 'AuthzConfigError', message: ['fs:compact'] },
    steps: [],
  },
  {
    name: "control: mode 'off' maps nothing, so the domain boots",
    world: fsWorld(unregistered('off')),
    steps: [fsRaw('uploads', true)],
  },
  {
    name: 'control: a filesystem checked in another domain does not fail this one',
    world: fsWorld({ uploads: { mode: 'enforce', domain: 'elsewhere', operations: { compact: 'fs:compact' } } }),
    steps: [fsRaw('uploads', false)],
  },
  {
    name: 'control: with the permission registered the domain boots and the method is checked',
    world: fsWorld(unregistered('enforce'), [{ name: 'fs:compact', types: ['fs', 'dir', 'file'] }]),
    steps: [
      as('alice', fsCall('uploads', 'compact', ['a.txt'], 'resolves')),
      { calls: { model: 'm1', atLeast: 1 } },
      fsCall('uploads', 'compact', ['a.txt'], { throws: 'AccessDenied', reason: 'unattended' }),
    ],
  },
];
```

Note for harness authors: a world whose `authz.fs` entry has no `domain` is checked in the harness's test

## (c) B28.signedUrl and `FsProviderSpec.signedUrl`

B28's note leaves `signedUrl` to L7: it needs a provider that signs URLs. Proposed:

```ts
export interface FsProviderSpec {
  // …
  /**
   * The provider signs URLs: the harness gives it `signedUrl(path, { until })` and `getSignedUrl(path, until)`,
   * the provider's own signer where it has one, else a fake whose URL carries `expires=<epoch ms>`.
   */
  readonly signedUrl?: boolean;
}
```

New part `B28.signedUrl` (`facets: ['engine', 'host', 'fs']`; data in `test/proposed/B28-signed-url.ts`).
World: `uploads` enforced, holds `docs/a.txt`, `signedUrl: true`; m1 permits alice the listed permissions on
every file, with `validUntil` = now + the given seconds when set. A step reads the URL's lifetime from
`X-Amz-Expires` (S3 presigned URL) or from `expires` minus the domain clock (fake signer).

| Case | m1 permits alice | `authz.fs.uploads` adds | Steps as alice | Expected |
|---|---|---|---|---|
| enforce: signedUrl needs fs:share on the file | `fs:share` | | `signedUrl(A)` | resolves |
| enforce: signedUrl without fs:share is AccessDenied, fs:read is not enough | `fs:read`, `fs:stat` | | `signedUrl(A)` | AccessDenied |
| enforce: getSignedUrl needs fs:share too | `fs:read` | | `getSignedUrl(A)` | AccessDenied |
| without an asked until the URL lives signedUrl.defaultTtlSeconds, 900 by default | `fs:share` | | `signedUrl(A)`, `getSignedUrl(A)` | 890–900 s |
| signedUrl.defaultTtlSeconds sets that lifetime | `fs:share` | `signedUrl: { defaultTtlSeconds: 300 }` | `signedUrl(A)` | 290–300 s |
| signedUrl.maxTtlSeconds caps the URL below the default | `fs:share` | `signedUrl: { maxTtlSeconds: 60 }` | `signedUrl(A)`, `getSignedUrl(A)` | 50–60 s |
| the permit's validUntil caps the URL | `fs:share`, valid 120 s | | `signedUrl(A)` | 110–121 s |

`FsArg` has no `DateTime`, so an asked `until` is not in the data; L7's unit tests (`test/signed-url.test.ts`)
cover it. L7 runs the part on fsNative and fsTemp (fake signer) and on fsS3 with `S3UrlSigner` (localstack).

L7's data sets `validUntil` from the wall clock (`Date.now()`), while the guard counts from the domain clock;
this holds only because the kit clock starts at wall time, and the 121 s bound allows for the drift. The kit
version should take `validUntil` from the session clock, so it stays right under a fixed `world.now`. The S3
lifetimes still need the kit clock near wall time, since the S3 signer measures `until` against the wall clock.

## (d) Cases that cannot hold on S3

B28.fs passes on fsNative and fsTemp (55 of 55). On fsS3, 53 of 55 pass; two fail for provider reasons, not
guard reasons. Two cases of the proposed B16.fs-owner fail on S3 for the same kind of reason.

| Part | Case | Why it cannot hold on fsS3 |
|---|---|---|
| B28.fs | resolvePath, tmppath and tmpname are not checks | `fsS3.resolvePath` of a relative path and `fsS3.tmppath` throw `MethodNotImplemented` |
| B28.fs | enforce: unzip needs fs:read on arch.zip and fs:write on unz | `fsS3.unzip` extracts through fsNative, which calls `dstFs.resolvePath`: it cannot extract onto S3 |
| B16.fs-owner | moving a directory onto another user's directory … | S3 has no directories: `isDir` is always false, so the guard checks the directory as a file, and `move` moves one key |
| B16.fs-owner | unzipping into another user's directory … | as the B28 unzip case |

The guard does its part in each: L7's S3 run keeps them as pending tests titled with the reason and runs
`B28.fs-s3`, which shows on S3 that `tmpname` resolves, that `resolvePath` and `tmppath` reach fsS3 unchecked
(its `MethodNotImplemented`, no model call, though the caller is UNATTENDED), and that `unzip` with both grants
passes the guard (m1 asked, fsS3's `MethodNotImplemented`, not `AccessDenied`).

Proposed kit change: a facet `fs-local` that a harness declares when its providers have local paths and real
directories (fsNative, fsTemp over fsNative; not fsS3), and:

- B28.fs: the case becomes "tmpname is not a check" (`tmpname` resolves, m1 not called); the denial cases of
  `unzip` stay.
- New part B28.fs-local (`facets: ['engine', 'host', 'fs', 'fs-local']`): "resolvePath and tmppath are not
  checks" (both resolve, m1 not called) and "enforce: unzip needs fs:read on arch.zip and fs:write on unz".
- B16.fs-owner (see (e)): the two directory cases go to a part B16.fs-owner-local with the `fs-local` facet.
- New part B28.fs-s3 (`facets: ['engine', 'host', 'fs', 'fs-s3']`, declared by a harness whose providers are
  fsS3) with the two cases of L7's `test/support/on-s3.ts`: "resolvePath, tmppath and tmpname are not checks:
  fsS3 answers them itself" (as UNATTENDED: `tmpname` resolves, `resolvePath('docs/a.txt')` and `tmppath()` throw
  `MethodNotImplemented`, m1 not called) and "enforce: unzip with fs:read on arch.zip and fs:write on unz passes
  the guard; fsS3 cannot extract onto S3" (`MethodNotImplemented`, m1 called at least twice). Without it the kit
  would never show on S3 that those calls skip the model; if the kit prefers no provider-shaped facet, that gap
  should be stated in the B28 note instead.

A strict S3 run then names its parts (`'B28.fs'`, `'B16.fs-owner'`) instead of the bare ids, since a strict run
fails a part whose facets the harness lacks.

No B28.fs case fails on fsTemp.

## (e) B16.fs-owner

The kit's B16.fs note leaves the owner grant of design §8.2 to L7. It belongs in the kit: it is the only data
that runs the `owner` relation through RBAC, the guard and a `FileMetadataStore` together. Proposed part
`B16.fs-owner`, `facets: ['engine', 'host', 'rbac', 'fs']` (data in `test/proposed/B16-owner.ts`).

World: rbac only; `uploads` enforced with `metadata: 'MemoryFileMetadataStore', stampOwner: true`, holding
`old.txt`; role `user` for alice and bob with `fs:read` and `fs:delete` by relation `owner` and `fs:write`, all on
`{ type: 'fs', id: 'uploads' }`. The harness must register an in-memory `FileMetadataStore` under that class
name, emptied per case (L7's `MemoryFileMetadataStore`, `test/support/memory-store.ts`); the kit should state
this in the fs facet's harness notes.

| Case | Steps | Expected |
|---|---|---|
| a file alice writes is stamped with her: she reads it, bob does not | alice writes and reads `mine.txt`; bob reads it | bob AccessDenied |
| a file written through a stream is stamped once the stream closes | alice `writeStream('s.txt')` (closed by the handle), reads it; bob reads it | alice resolves, bob AccessDenied |
| a file nobody stamped has no owner: present at setup, or written by SYSTEM | alice reads `old.txt`; SYSTEM writes `sys.txt`; alice reads it | both AccessDenied |
| rm drops the owner: a file SYSTEM writes later at that path is not the old owner's | alice writes, removes `a.txt`; SYSTEM writes it; alice reads it | AccessDenied |
| only the owner deletes; a denied rm keeps the file and its owner | alice writes `a.txt`; bob `rm`; alice reads | bob AccessDenied, alice resolves |
| move: the owner follows the file, and the old path is no longer theirs | alice writes `a.txt`, moves it to `docs/b.txt`, reads it; bob reads it; SYSTEM writes `a.txt`; alice reads it | alice resolves on `docs/b.txt`, bob AccessDenied, alice AccessDenied on the new `a.txt` |
| append keeps the first owner | alice writes `a.txt`; bob appends, reads; alice reads | bob's append resolves, his read AccessDenied, alice resolves |
| an overwrite keeps the first owner: fs:write on a file gives no owner rights over it | alice writes `a.txt`; bob writes it, reads it, `rm`; alice reads | bob's write resolves, read and rm AccessDenied, alice resolves |
| renaming a file onto an existing one keeps its first owner | alice writes `a.txt`; bob writes `b.txt`, renames it onto `a.txt`, reads, `rm`; alice reads | rename resolves, bob's read and rm AccessDenied, alice resolves |
| moving a directory onto another user's directory does not take it over … (`fs-local`) | alice `mkdir alice-dir`, writes `alice-dir/secret.txt`; bob `mkdir bob-dir`, writes `bob-dir/x.txt`, moves `bob-dir` onto `alice-dir`, `rm alice-dir`; alice reads `alice-dir/secret.txt` | move resolves, rm AccessDenied, alice resolves |
| unzipping into another user's directory does not take it over … (`fs-local`) | alice `mkdir alice-dir`, writes `alice-dir/a.txt`; bob writes `b.txt`, zips it to `bob.zip`, unzips into `alice-dir`, `rm alice-dir`; alice reads `alice-dir/a.txt` | unzip resolves, rm AccessDenied, alice resolves |

## (g) Design §8 and §13: config keys L7 added

To add to design §13 (and the §8 config list):

- `authz.fsMetadata.connection` (default `'default'`): the ORM connection of `OrmFileMetadataStore` and of its
  migration `AuthzFsObject_2026_10_01_00_00_00`. It is not under `authz.fs`, which is keyed by filesystem name: a
  `metadata` key there would be read as a filesystem entry without a mode and fail every boot.
- `authz.fs.<name>.signedUrl.defaultTtlSeconds` (default 900): the lifetime when the caller asks no `until`. The
  TTL rule becomes `until = min(asked ?? now + defaultTtlSeconds, now + maxTtlSeconds, decision.validUntil)`,
  absent terms ignored, now from the domain's `AuthzClock` (D9 rev.).
- `authz.fs.<name>.operations`: method → permission or list of permissions, checked on argument 0. It adds
  methods or replaces a method that checks one path (keeping its `file`/`dir` kind). Replacing a method that checks
  more than argument 0 (`copy`, `move`, `rename`, `zip`, `unzip`, `upload`) or mapping an unchecked member
  (`resolvePath`, `tmppath`, `tmpname`, DI lifecycle) is an `AuthzConfigError`. Its permissions are boot refs of
  the domain (rule 7, B02.adapter).
- `authz.fs.<name>.list`: `'dir'` (default, `fs:list` on the directory) or `'each'` (also `fs:stat` per entry;
  enforce drops denied entries, audit keeps them and warns).
- A present `authz.fs.<name>` entry must state `mode`; unknown keys are refused.
- §13 says "fs-only policies (`authz.fs.policies`)": the key is `authz.fs.<name>.policies`, and each policy is
  scoped to its filesystem (a policy without `scope` gets `{ type: 'fs', id: <name> }`; `fs:` permissions and
  `fs`/`dir`/`file` resource types only).

## (h) Design §13 errata

- Bullet 2 says `fsService.resolve()` applies the decorators "before `asMapValue('__file_provider_instance__',
  …)`". It does not, and must not: fsService creates every provider and publishes the raw instance first (fsTemp
  and other providers look their backends up by name in their own `resolve()` and must keep the raw ones), then
  applies the decorators in ascending `order` and replaces each map entry with the decorated instance. If a
  decorator throws, every provider of that resolve is unpublished, so no raw provider stays reachable through
  `getFs` (commit "fix(fs): unpublish every provider when a decorator throws").
- Ancestors of an fs ref are `[self, parent directories nearest first, { type: 'fs', id }, GLOBAL]`. Domain
  parents from `FsPathResolver` are not ancestors: they would break the tree rule (`ancestors(parent)` is the tail
  of `ancestors(child)`) whenever a resolver answers only for deeper paths. `fs-inherit` reads the resolver
  instead (D4 rev.).
