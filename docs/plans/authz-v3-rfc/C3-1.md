# C3-1: grants with the same condition intersect their fields (guest plus user loses Email)

Status: proposed (C3, 2026-10-05). APPROVED; point 1 APPLIED by F8 (2026-10-08): `residualWith` groups
conditional grants by structurally equal permit filters (`sameFilter` in `model/same-filter.ts`), design §6.1.2 step 9 updated, C3's users
test flipped. Point 2 (engine `FieldCombiner`) not taken; `nativeListVote` still intersects (fails closed).

## Problem

Users ships two roles that read a user's own row (`packages/users/src/config/users.ts`, design §8.2):

```ts
guest: { grants: [{ permission: 'user:read', relation: 'self', fields: { read: ['Login'] } }] },
user:  { grants: [{ permission: 'user:read', relation: 'self', fields: { read: ['Email', 'Login'] } }, …] },
```

Both grants are conditional (`self`), so on a check authz-rbac's vote takes the INTERSECTION of their field sets
(`voteFieldGlobs` in `packages/authz-rbac/src/model/fields.ts`, called from `residualWith` in `model/evaluate.ts`):
when no unconditional grant permits the row, the vote's fields are the intersection over every conditional grant that
permits some row. An account holding `guest` and `user` reads its own row with `Login` only, though `user` alone gives
`Email` too. An application that gives every account `guest` (as a base role next to `user`, or through
`defaultRoles`) loses `Email` for all its users. The access summary shows the same: `AuthzService.summary` takes an
entry's fields from a type-level check, which intersects too; only the per-model summaries (`summaryFieldGlobs`) list
the union.

The intersection is there because a vote has one field set for all its rows, and a union over grants that may hold on
different rows would give a row the fields of a grant that does not hold on it. That reason does not apply to grants
whose conditions are the same: they hold on exactly the same rows. Intersecting them is needlessly strict.

C1 worked around it by shipping `guest` with `['Email', 'Login']`, which gives a guest-only account its `Email`, against
§8.2. C3 restored §8.2 (`guest` reads `['Login']`) and pins today's result for the combination in
`packages/users/test/shipped-config.test.ts` ("RFC C3-1: an account holding guest and user reads its own row with
Login only (intersection, fail closed)"), in the check and in the summary entry.

## Change (authz-rbac, then possibly the engine)

1. Preferred form: group inside `residualWith` (`model/evaluate.ts`) and leave the public field functions alone.
   `residualWith` collects the conditional grants as `{ key, fields }`, groups them by key, takes the union of each
   group's field sets (a grant without fields stands for every field, as today) and passes one entry per group as
   `conditional` to `fieldGlobs`. Unconditional grants keep today's rule (their union decides).
   `voteFieldGlobs`, `summaryFieldGlobs` (a union of unions is the same union), `FieldRule`, `withFieldRule`,
   `steps.fieldGlobs` and `nativeListVote` (`model/rules/native.ts`) keep their signatures and code; all of them are
   public exports of `@spinajs/authz-rbac` (`model/index.ts`). A custom `FieldRule` then gets one `conditional` entry
   per group instead of one per grant; the release notes say so. Changing `voteFieldGlobs` to take
   `{ filter, fields }` pairs gives the same result but breaks the `FieldRule` extension point; do not.

   The key of a grant is the filter `residualWith` already computes for it, `permits` =
   `and(grantResidual(grant, at), c.rows)` (for scoped grants also `scopedRows(holders)` and the checks). It covers the
   relation set, the bound `on` patterns, `requiresTag`, `grantedAt` and the holders' rows in one comparison; equal
   grant attributes alone (same relations, `on`, `requiresTag`, `grantedAt`) are not enough when the holders' rows
   differ.

   Two grants share a group only when their simplified `permits` filters are equal by exact structural equality over
   the `ResourceFilter` grammar, or by a canonical form that is injective over that grammar and answers "none" for any
   value it cannot serialise, as `canonical(...)` in `packages/authz/src/engine/cache-key.ts` does for cache keys
   (own enumerable data properties of plain objects and arrays only, a work budget, failure ⇒ no key). Plain
   `JSON.stringify` is not enough: the `native:*` node carries `args?: unknown`
   (`packages/authz/src/contracts/filter.ts`), and `JSON.stringify` drops `undefined` and functions, writes `Map` and
   `Set` as `{}` and throws on `bigint`, so two different filters could compare equal and union their fields onto rows
   only one of them permits (fail open). A grant whose filter has no canonical form is a group of its own.

   Tests for the implementer (L1): two conditional grants that differ only in a `native:*` arg (for example
   `new Map([['a', 1]])` against `new Map([['b', 1]])`, or `{ x: undefined }` against `{}`) keep the intersection;
   a `native:*` arg with no canonical form (a function, a class instance) keeps the intersection; two grants with
   equal `permits` filters get the union.

   Point 1 also fixes the `AuthzService.summary` entry: it takes the entry's fields from `quietCheck`, a type-level
   check through the same `residualWith` (`packages/authz/src/engine/authorizer.ts`). `RbacModel.summarize` already
   unions (`summaryFieldGlobs`) and needs no change.

2. Engine, `FieldCombiner.combine` with `firm` (`packages/authz/src/engine/fields.ts`): the same reasoning applies.
   When no vote's bound term is TRUE, it intersects the fields of every conditional vote. Votes whose bound terms are
   equal hold on the same rows; grouping them by the simplified bound term (union within, intersection across) is
   sound by the same argument and needs the same equality. This is optional: users' case is inside one RBAC vote and
   needs only point 1.

## Proof sketch

Let the conditional grants fall into groups G1…Gk with conditions C1…Ck (every grant in Gi permits exactly the rows
of Ci). The vote's fields become F = ∩i (∪g∈Gi fields(g)). Take any row r the vote permits: r satisfies some Cj, so
every grant in Gj holds on r, and F ⊆ ∪g∈Gj fields(g). Each field in F is therefore given by a grant that holds on r,
which is the property the intersection protects today. With every grant in its own group this is today's rule; since
∩ of the unions ⊇ ∩ of the single sets, the change never yields fewer fields than today. The proof needs grants in one
group to permit exactly the same rows, so the comparison must never call two different filters equal (point 1). A
comparison that misses an equal condition (two spellings of one filter, or a filter with no canonical form) only
splits a group, which falls back to today's result: fail closed.

## Why the users fragment cannot fix it

The fragment can only choose the field set of each role. With intersection, the combination reads
fields(guest) ∩ fields(user), so `Email` reaches a `guest`+`user` account only if `guest` lists `Email`, and then a
guest-only account reads `Email` too (C1's workaround). Dropping `relation: 'self'` from either grant makes it
unconditional and lets it read every user's row; dropping guest's grant leaves a guest without its own `Login`. No
fragment gives guest `Login` only and guest plus user `Email` and `Login`.

## Affected lanes

- L1: `residualWith` in `model/evaluate.ts` (point 1); `voteFieldGlobs` and `FieldRule` stay as they are.
- F3/E1: `FieldCombiner` firm path, if they take point 2.
- C3: flip the RFC C3-1 test in `packages/users/test/shipped-config.test.ts` to expect `Email` and `Login` (check and
  summary entry) once point 1 lands.
