# C1-1: B12.write fails with users' shipped `admin` roles (glob grants and the escalation guard)

Status: applied by G2 (2026-10-05, `fix(authz-rbac): cover glob grants against the permission registry` on
`authz/G2-admin-guard`): option 1, failing closed. Proposed by C1 (2026-10-05); owners of the possible changes: L9 (the
`AuthzAdmin` guard in `@spinajs/authz-rbac`), C2 (the `users:*` permissions), C1 (users' role fragment), the
`@spinajs/authz-testing` kit.

What was applied: `CheckRbacAdminFacts.covers` expands each grant as the model's `compileGrants` does, a glob to the
registered permissions it matches and every grant to what those imply, and asks the actor to hold each one, with
the grant's field set, unconditionally. Unlike option 1 below, a glob that matches no registered permission, an
invalid glob and a domain with no registry count as not covered. So B12.write still fails with users' fragment:
`user.metadata:*` matches nothing in the B12 world (no package registers a `user.metadata` permission yet), and
`packages/users/test/acceptance.test.ts` still leaves B12.write out. It can run once C2 registers those permissions
and the world's `superuser` holds them (option 2).

## Problem

Plan C1's acceptance runs B12 (part `write`) with users' role config fragment (`packages/users/src/config/users.ts`,
`authz.rbac.roles`), merged with the world's roles as an application loads both (lists concatenated). The B12 world
reuses the names users ships: `admin.users` (not assignable) and `admin` (extends `admin.users`). Users' fragment, as
design §8.2 writes it, gives them:

```ts
'admin.users': { assignable: false, grants: ['users:*', 'user.metadata:*'] },
admin: { extends: ['admin.users'], grants: ['user:impersonate'] },
```

The case "a write assigning a role that extends a non-assignable one is accepted and inherits its grants" has
`user:root` (role `superuser`, which holds every permission of the world) grant `admin` at GLOBAL. With the fragment
merged it fails:

```
escalation: user:root may not grant "admin" at {"type":"$global"}: it does not hold every permission of the role there
```

`CheckRbacAdminFacts.covers` (`packages/authz-rbac/src/admin/facts.ts`) fails closed on a glob grant ("a glob grant …
counts as not covered"), and `admin` now inherits `users:*` and `user.metadata:*`. The other three B12.write cases and
B10.rbac and B27.events pass with the fragment; B12.write passes in full without it (checked).

This is not only a fixture matter. With users' shipped roles, no principal but SYSTEM can grant `admin`, or any role
that extends `admin.users`, through `AuthzAdmin`: the escalation check refuses every human admin, whatever they hold.
`users:*` and `user.metadata:*` are globs because no package declares the `users:*` or `user.metadata:*` permissions yet
(review 5 M6, hand-off to C2).

## Options

1. **L9: cover globs against the registry.** `covers` expands a glob grant to the registered permissions it matches
   (the RBAC model already compiles globs that way) and requires the actor to cover each; a glob that matches nothing
   counts as covered. B12.write then passes with the fragment, unchanged.
2. **C2 then C1: name the permissions.** C2 declares the `users:*` (and `user.metadata:*`) permissions; C1 replaces the
   globs in its fragment with those names. The B12 world's `superuser` would still lack them, so the kit world would
   also have to grant them to `superuser` (option 3).
3. **Kit: keep the world independent of users' names.** Rename the B12 roles (for example `admin.pkg` and `admin.app`)
   so a lane's shipped roles cannot merge into them. This hides the product problem above rather than fixing it.

C1 proposes option 1 (the product behaviour), and option 2 when C2 lands.

## What C1 does meanwhile

`packages/users/test/acceptance.test.ts` runs B10.rbac and B27.events with users' fragment merged, and does not run
B12.write (that part stops until this RFC is decided). Users' own B12 write path stays covered by its tests:
`create.test.ts` (default roles assigned through `AuthzAdmin` as SYSTEM, `unknown_role` and `not_assignable` refused),
`role-assignments.test.ts` (grant and revoke through `AuthzAdmin`, the guard with an actor) and the acceptance file's
`RoleAssigned`/`RoleRevoked` cases for `create`, `grant` and `revoke`.

## Affected lanes

- L9 (option 1), C2 and C1 (option 2), the kit owner (option 3).
- C4 runs B12.http against its own roles; not affected unless it merges users' fragment too.
