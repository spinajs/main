# G2-1: AuthzAdmin's last-holder check counts only accounts in service

Status: APPROVED by the controller (inversion: an optional authz-rbac port that users implements; options 1
to 3 below rejected) and APPLIED by G2b (2026-10-05) on `authz/G2b-account-status`:
`feat(authz-rbac): count only accounts in service as last holders` (d6c47df08),
`feat(users): report accounts in service to the admin guard` (053b830c0),
`fix(authz-rbac): refuse malformed account status answers` (6ae8ac721),
`fix(users): count invite-pending accounts as out of service` (d0372602f). No frozen file changed, no
rule-10 exception. Proposed by G2 (2026-10-05).

## Decision (controller)

- authz-rbac declares an optional abstract class of its own, `AccountStatusSource`
  (`packages/authz-rbac/src/admin/ports.ts`, exported from the admin barrel; not a frozen file):
  `inService(refs: readonly PrincipalRef[]): Promise<ReadonlyMap<string, boolean>>`, keyed by `principalKey`.
  authz-rbac still imports neither authn nor users.
- users implements it over its own user rows and registers it (`UserAccountStatusSource`).
- `last_holder` counts a remaining sure holder only when the source answers exactly `true` for it. A source that
  throws (on `resolve` or on `inService`), an answer that is not a Map or not a boolean `true`, or a ref the
  answer leaves out: that holder does not count, so the removal is refused `last_holder` when nobody else surely
  holds the permission (fail closed). The failure is logged at warn level with the error name and message (no
  stack), once per guard call.
- No source registered: the old count, and one warning. It fires on the first guard call that needs the source,
  once per `DefaultAdminGuard` instance (a root singleton, so once per process): authz-rbac's admin side has no
  boot hook, and checking at boot would resolve eagerly (F4).
- The guard resolves the source lazily from `adminContainer(ctx)` (`hasRegistered`, then `resolve`), and asks it
  only when a removal lies on a path to `privilegedPermission`, once per guard call, with the distinct refs of
  the remaining sure holders. Non-user principals go to the source too; the source decides. Links never count.
  `self_lockout` is unchanged.

Options 1 to 3 below are rejected. Option 1 changes a frozen contract. Option 2 breaks rule 10. Option 3, as
written, makes the port the only way to judge a holder (no implementation means only SYSTEM can remove a GLOBAL
privileged path, so every app with its own identity store must ship one first) and reads state through
`IdentityStore.status`, which does not report an expired password. The decision keeps the port optional, lets
the implementer read its own records, and takes one batch call per guard call.

## As applied (G2b): in service in users

`packages/users/src/identity/account-status.ts`. A `user` ref is in service when its row:

- exists and is not soft-deleted (`DeletedAt` empty; read `withDeleted()`);
- is active (`IsActive`);
- is not banned (the `IsBanned` getter: a timed ban counts until start + duration);
- has no pending invite (metadata `USER_COMMON_METADATA.USER_INVITE_PENDING` is not `true`, as
  `UserIdentityStore.status` reads it; users' own `create()` already leaves invited rows inactive, but an app
  hook may set them active);
- has a password other than authn-local's `EXPIRED_PASSWORD_MARKER`. Both expiry routes write the marker: an
  admin expire-password (`PasswordExpiry` `cause: 'admin'`) and the `authn.local.expiration` job
  (`cause: 'aged'`). A password past `maxAgeDays` that the job has not marked still logs in, so age alone does
  not put an account out of service. An active account with no password (`NO_PASSWORD`, e.g. OIDC only) is in
  service.

Any other principal type, and a Uuid with no row, is out of service. Rows are read in chunks of 100 with their
metadata (ban and invite live there); every ref gets an answer.

Tests: authz-rbac `test/admin/guard-account-status.test.ts` (table model) and
`guard-account-status.rbac.test.ts` (real model on `rbacAdminHarness`); users `test/account-status.test.ts`
(source states, and the acceptance case in process: the last active admin cannot be revoked while a banned, a
deactivated and a deleted admin exist; users has no `/authz/*` HTTP harness).

Not covered (as below): races between two batches; users-http's `AccountGuard` still runs its own witness search
and counts an expired-password account as a witness (a C2 follow-up).

## Original proposal

### Problem

`DefaultAdminGuard`'s `last_holder` check (design §6.6.2) counts every principal with a sure path to
`privilegedPermission` at GLOBAL, whatever the state of its account. A revoke sent to `AuthzAdmin`
directly (`/authz/*` or in process) can therefore take the privilege from the last active admin
while a deactivated, banned, deleted or expired account still "holds" it. C2 closed the same gap on
the users-http routes with its own `AccountGuard` (design §6.6.2, "Open (L9/G2)"); the core path
does not hold.

### Why G2 stops here

The design's account-state hook is authn's `IdentityStore.status(id): IdentityStatus` (§22.3,
`packages/authn/src/contracts/identity.ts`), which `@spinajs/users` implements. The guard lives in
`@spinajs/authz-rbac`, which may not depend on `@spinajs/authn` (plan §1 rule 10: only
`packages/authz/package.json` lists it; authz sources import only `@spinajs/authn/contracts`), and
`@spinajs/authz` does not re-export `IdentityStore`. Reaching it needs one of:

1. **Re-export (preferred).** `packages/authz/src/contracts/principal.ts` (frozen) re-exports
   `IdentityStore` and the type `IdentityStatus` from `@spinajs/authn/contracts`, the way it already
   re-exports `SYSTEM`, `principalKey` and the principal types. authz-rbac imports them from
   `@spinajs/authz`. No new dependency; the api snapshot of authz gains two names.
2. **Dependency exception.** authz-rbac lists `@spinajs/authn` and imports
   `@spinajs/authn/contracts` directly (rule 10 exception; R1's grep gate must allow it).
3. **A new authz-rbac port.** An abstract `AdminAccountState` in `authz-rbac/src/admin/**` that users
   implements over its `IdentityStore`. No frozen file changes, but a second hook for the same fact,
   and every app with its own identity store must implement it too.

Two routes need no frozen change but are rejected:

- An `AuthzCommandValidator` in users: it runs before the transaction, one command at a time and
  for SYSTEM too, so a batch that revokes the last two active holders would pass.
- A users guard named in `authz.admin.guard.service` that wraps `DefaultAdminGuard`: it moves a
  core rule into an app package and has to redo the guard's private path logic.

### Proposed behaviour (any option; superseded by the decision above)

- `last_holder`: a remaining holder counts only if its principal is in service. For a `user`
  principal: `IdentityStore.status({ type: 'user', id })` answers
  `exists && active && !banned && !deleted && !invitePending`; an expired account (users' expiry) must read as not active, which
  `UserIdentityStore` has to confirm. Principals of other types (service, agent: an open N1 question,
  §22.3) do not count, so a domain whose only remaining holders are services refuses (over-refusal,
  fail closed). Links already never count.
- Fail closed: no `IdentityStore` registered while a user holder must be judged ⇒ the holder does
  not count (the removal is refused `last_holder` when nobody else surely holds it), so without an
  `IdentityStore` only SYSTEM can remove a GLOBAL privileged path; a `status` call that throws ⇒
  that holder does not count. The "held before" side stays loose, as today.
- The lookup runs only when a removal lies on a path to `privilegedPermission`, once per distinct
  holder per guard call, and is resolved lazily (no eager `AuthzService` or store injection, F4).
- Not covered: races between two batches that each remove a different last active holder (also
  true of C2's `AccountGuard`); `self_lockout` is unchanged (the actor is in service by definition).

### Tests (proposed; see "As applied" for what G2b wrote)

Table model: a banned / deactivated / deleted / invite-pending user holder is not counted; an active
one is; `status` throwing and no `IdentityStore` both refuse. Real model on `rbacAdminHarness` with a
fake `IdentityStore`. users: a run with `UserIdentityStore` over real records (C1/C2 test harness).

### Affected lanes

G2 (guard), F1/F6 owner (option 1) or the plan owner (option 2), C1/C2 (`UserIdentityStore` must
answer expiry; users-http's `AccountGuard` may then defer to the core check), M1 (docs).
