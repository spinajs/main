# G2-1: AuthzAdmin's last-holder check counts only accounts in service

Status: proposed (G2, 2026-10-05). Needs a decision by the controller. Owners of the possible
changes: F1/F6 contracts (a re-export in `@spinajs/authz`), the plan's dependency rule 10, L9/G2
(`DefaultAdminGuard` in `@spinajs/authz-rbac`).

## Problem

`DefaultAdminGuard`'s `last_holder` check (design §6.6.2) counts every principal with a sure path to
`privilegedPermission` at GLOBAL, whatever the state of its account. A revoke sent to `AuthzAdmin`
directly (`/authz/*` or in process) can therefore take the privilege from the last active admin
while a deactivated, banned, deleted or expired account still "holds" it. C2 closed the same gap on
the users-http routes with its own `AccountGuard` (design §6.6.2, "Open (L9/G2)"); the core path
does not hold.

## Why G2 stops here

The design's account-state hook is authn's `IdentityStore.status(id): IdentityStatus` (§22.3,
`packages/authn/src/contracts/identity.ts`), which `@spinajs/users` implements. The guard lives in
`@spinajs/authz-rbac`, which may not depend on `@spinajs/authn` (plan §1 rule 10: only
`packages/authz/package.json` lists it; authz sources import only `@spinajs/authn/contracts`), and
`@spinajs/authz` does not re-export `IdentityStore`. Reaching it needs one of:

1. **Re-export (preferred).** `packages/authz/src/contracts/principal.ts` (frozen) re-exports
   `IdentityStore` and the type `IdentityStatus` from `@spinajs/authn/contracts`, the way it already
   re-exports `SYSTEM`, `principalKey` and the principal types. authz-rbac imports them from
   `@spinajs/authz`. No new dependency; the api snapshot of authz gains two names.
2. **Dependency exception.** authz-rbac lists `@spinajs/authn` and imports
   `@spinajs/authn/contracts` directly (rule 10 exception; R1's grep gate must allow it).
3. **A new authz-rbac port.** An abstract `AdminAccountState` in `authz-rbac/src/admin/**` that users
   implements over its `IdentityStore`. No frozen file changes, but a second hook for the same fact,
   and every app with its own identity store must implement it too.

Two routes need no frozen change but are rejected:

- An `AuthzCommandValidator` in users: it runs before the transaction, one command at a time and
  for SYSTEM too, so a batch that revokes the last two active holders would pass.
- A users guard named in `authz.admin.guard.service` that wraps `DefaultAdminGuard`: it moves a
  core rule into an app package and has to redo the guard's private path logic.

## Proposed behaviour (any option)

- `last_holder`: a remaining holder counts only if its principal is in service. For a `user`
  principal: `IdentityStore.status({ type: 'user', id })` answers `exists && active && !banned &&
  !deleted && !invitePending`; an expired account (users' expiry) must read as not active, which
  `UserIdentityStore` has to confirm. Principals of other types (service, agent: an open N1 question,
  §22.3) do not count, so a domain whose only remaining holders are services refuses (over-refusal,
  fail closed). Links already never count.
- Fail closed: no `IdentityStore` registered while a user holder must be judged ⇒ the holder does
  not count (the removal is refused `last_holder` when nobody else surely holds it), so without an
  `IdentityStore` only SYSTEM can remove a GLOBAL privileged path; a `status` call that throws ⇒
  that holder does not count. The "held before" side stays loose, as today.
- The lookup runs only when a removal lies on a path to `privilegedPermission`, once per distinct
  holder per guard call, and is resolved lazily (no eager `AuthzService` or store injection, F4).
- Not covered: races between two batches that each remove a different last active holder (also
  true of C2's `AccountGuard`); `self_lockout` is unchanged (the actor is in service by definition).

## Tests (to write first, once approved)

Table model: a banned / deactivated / deleted / invite-pending user holder is not counted; an active
one is; `status` throwing and no `IdentityStore` both refuse. Real model on `rbacAdminHarness` with a
fake `IdentityStore`. users: a run with `UserIdentityStore` over real records (C1/C2 test harness).

## Affected lanes

G2 (guard), F1/F6 owner (option 1) or the plan owner (option 2), C1/C2 (`UserIdentityStore` must
answer expiry; users-http's `AccountGuard` may then defer to the core check), M1 (docs).
