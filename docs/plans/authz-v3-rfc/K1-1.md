# RFC K1-1: the canvas config cannot write group members through AuthzAdmin

Status: PROPOSED.

Lane K1 (canvas C6 conformance), task 6. Owner of the change: design (§8.5, §6.6.4) and CV1.
No frozen contract changes.

## Problem

Design §6.6.4 writes a C6 group member as
`execute([{ kind: 'set.addMember', set: { role: 'group.member', scope: group:G }, member: user:U }])`,
and the §8.5 data row "Group member" says the same (`group.member` at `group:G`). AuthzAdmin checks
the command's permission at the set scope `group:G`, also when the actor is SYSTEM
(design §6.6.2: "SYSTEM passes, audited" applies to the decision, not to the type check).

The §8.5 config types every permission on `org`, `project`, `file`, `branch` only, and §6.6.4 maps
no permission for `set.*`. Whatever permission `authz.admin.permissions` names for `set.*`, the
engine refuses the check before any model votes
(`packages/authz/src/engine/authorizer.ts:857-859`):

```
AuthzConfigError: test: permission "org:manage" is checked on type "group", which is not in its
types (org, project, file, branch) or $global
```

So the §8.5 config, as written, cannot load the canvas state through AuthzAdmin: every org batch
that holds a group member rolls back. For an actor other than SYSTEM there is a second gap: the
canvas scope tree (§8.5 "Canvas code that remains": org → project → file → branch) has no `group`
node, so even with the type added, `org:manage` on `group:G` would not reach the actor's
`org.admin` assignment at `org:O` (the resolver answers `null` for `group:G`, i.e.
`unknown_resource`).

No C6 case checks a permission on a group, so no decision depends on this; it blocks the writes
only.

## Evidence

- K1 harness: without the workaround below the state load fails with the error above (review
  mutation m4: 67 tests fail).
- authz-rbac's own canvas admin scenario (`packages/authz-rbac/test/admin/canvas.test.ts:84`)
  already adds `group` to the types of every org permission to make `set.addMember` work.

## What K1 does now

`packages/authz-testing/test/canvas-c6/harness.ts` adds the type `group` to `org:manage` in the
test world only (`ADMIN_EXTRA_TYPES`) and maps `set.*` to `org:manage`. The generated §8.5 config
object is not touched. All 64 cases conform with it.

## Proposed change

Canvas side (design §8.5 and §6.6.4, then CV1), not SpinaJS:

1. §8.5: the generator gives `org:manage` (the permission §6.6.4 should name for `set.*`) the types
   `['org', 'project', 'file', 'branch', 'group']`.
2. §6.6.4: add the row "`set.*` (group members) → `org:manage`" to the capability mapping of
   `authz.admin.permissions`.
3. §8.5 "Canvas code that remains": the scope resolver also resolves `group:G → [group:G, org:O,
   GLOBAL]`, so an org admin who is not SYSTEM can add group members.

Alternative: give the canvas groups their own C6 capability typed on `group`. That changes C6's
capability table and the wire order, so it is the heavier option.

## Affected lanes

- K1: drop `ADMIN_EXTRA_TYPES` once the generator emits the type; add `group` to
  `CanvasScopeResolver` with a test.
- CV1: same in canvas's generator, resolver and S3 writes.
- Design owner: §8.5, §6.6.4.
