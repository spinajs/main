# RFC N3-1: a conditional password write on PasswordCredentialStore

Status: APPROVED (the optional `expected` on `set`, not the separate `replace`) and APPLIED 2026-10-04 (K3). The
frozen contract, its API snapshot and the design's §22 listing carry the new `set`; the kit's
`MemoryPasswordCredentialStore` implements it and `runIdentityStoreConformance` checks it; `LocalPasswordStrategy`
rehashes with `set(id, fresh, verified)` and no longer re-reads. The ORM and users stores follow by the hand-off below.

Lane N3 (authn-local), final lane review, finding I1. Frozen contract:
`packages/authn/src/contracts/identity.ts` (`PasswordCredentialStore`).

## Problem

After a successful login whose stored hash needs a rehash (A03: other argon2 parameters, an older or
missing pepper), `LocalPasswordStrategy` hashes the password again and stores the new hash. That hash
takes a full argon2 run and may wait in the limiter queue. If `redeemReset`, `set`, `change` or
`expire` stores a new value in that window, an unconditional write puts a hash of the old password
back. The owner's reset or the admin's expiry silently reverts, and whoever knows the old password
keeps logging in (A30, A11).

N3 now re-reads the stored value after hashing and writes only if it is still the value that was
verified (commit `884d97aa0`, tests in `packages/authn-local/test/strategy.test.ts`, "rehash racing
a credential change"). That closes the window around the hash. A smaller one remains between the
re-read and the write: two awaits with no hash between them, but still open to a concurrent writer,
on another instance too. The frozen contract offers only `get` and an unconditional `set`, so N3
cannot close it alone.

## Change (applied)

Add an optional expected value to `set`:

```ts
export abstract class PasswordCredentialStore {
  abstract get(id: IdentityRef): Promise<string | null>;
  /**
   * Stores the hash, never a raw password: hashing is the strategy's job (A03). With `expected`, writes
   * only when the stored value is still `expected` (compare-and-set, atomic in the store) and answers
   * whether it wrote; without it, writes unconditionally and answers true.
   */
  abstract set(id: IdentityRef, hash: string, expected?: string | null): Promise<boolean>;
}
```

- A SQL store does it in one statement: `UPDATE … SET password = :hash WHERE id = :id AND password =
  :expected` (`password IS NULL` when `expected` is null), and returns whether one row changed.
- Callers that do not pass `expected` keep today's behaviour. The `void` to `boolean` return change is
  compatible for callers that ignore the result, but every store that implements the contract must
  change its signature (users in C1, any app store).
- N3 then replaces its re-read with `set(id, fresh, verified)` and drops the comment that points here.
- The kit's `MemoryPasswordCredentialStore` gets the same check (F7).

An alternative is a separate `replace(id, expected, hash): Promise<boolean>`, which leaves `set` as it
is. Either serves N3.

## Affected lanes

- N3 (authn-local): uses the conditional write in the login rehash. Until then the re-read stays, and
  the lane is complete without this RFC.
- C1 (users): implements the conditional write in the users `PasswordCredentialStore`. A rehash and
  the `!expired` marker go through `set` too and are not a "password set" for `PasswordAgeSource`.
- N4 (authn-orm): implements it in the ORM-backed store, as one conditional `UPDATE`.
- F7 (authn-testing): the memory fake follows the contract.

## Hand-off to N4 (authn-orm) and C1 (users)

`PasswordCredentialStore.set` is now `set(id, hash, expected?: string | null): Promise<boolean>`. Every store
that implements it:

- Without `expected` (`undefined` or omitted): writes unconditionally and answers true, as before, whatever
  row count the driver reports.
- With `expected` a string: writes only when the stored value is exactly that string. With `expected` null:
  only in a stored state for which `get` answers null. Answers whether it wrote; a mismatch answers false and
  never throws. The contract leaves an identity the store does not know to the store.
- Does it as one conditional statement, never as a read followed by a write:
  `UPDATE … SET password = :hash WHERE id = :id AND password = :expected`. For null, match exactly the states
  `get` maps to null: `users.Password` is `NOT NULL`, so there it is whatever value stands for "no password"
  (e.g. `AND (password IS NULL OR password = '')`), never `= NULL`; a separate password table would use
  `INSERT … ON CONFLICT DO NOTHING`. Answer whether exactly one row matched (sqlite `changes`, postgres
  `rowCount`; on MySQL `affectedRows` counts changed, not matched, rows unless `CLIENT_FOUND_ROWS` is set;
  check what the ORM's update reports).
- Keeps `undefined` and `null` apart: never `expected ?? null` or a falsy test, which would turn an
  unconditional write into a conditional one or the reverse. Compares bytes exactly: no trimming, no
  case-insensitive collation.
- Keeps the third parameter. TypeScript accepts an override `set(id, hash)` that drops it, and such a store
  silently ignores `expected`: since the strategy no longer re-reads, a rehash then writes the old password
  back over a concurrent reset or expiry. The same holds for any app store.
- Passes `runIdentityStoreConformance` from `@spinajs/authn-testing`, run against the real store: four cases
  cover `set`, including eight parallel conditional writes over one value of which exactly one may win.

N4: authn-orm merged (`65c1da98d`) without a `PasswordCredentialStore`, and the plan gives the `users.Password`
store to C1, so the store side lands in C1. If authn-orm ever adds an ORM-backed store, it implements the above. C1: a rehash and the `!expired` marker go through `set` too
and are not a "password set" for `PasswordAgeSource`.

## Follow-ups (not in this RFC)

- `LocalPasswordService.change` verifies the old password, hashes the new one and then writes without a
  condition, so an admin expiry or a reset that lands in that window is overwritten (A30, A11). Fix in
  authn-local (owner: the N3 lane, or an RFC N3-2 if it needs a contract change): `verifyPassword` returns
  the value it checked, `storePassword` passes it as `expected`, and a lost write audits a failure, answers
  invalid and neither revokes nor rotates sessions.
- A login verified just before a concurrent expiry can still get a session issued after the expiry's
  `revokeAll`. The window exists for every login, not only for a rehash, so it belongs to `AuthnService` and
  session issue.
