# L1-1 Roles named in RBAC config

Status: proposed by L1 (task 3). Asks the kit owner for fixture cases; changes no contract.

## Question

The B12 fixture note leaves one point to an L1 RFC. B12 refuses "`assignable: false` targets of an
assignment" with `AuthzConfigError` for config. Design §6.1 and §8.2 do not say which config keys
assign roles, or what happens when such a key names a bad role. §8.2 has three keys that name roles:

- `authz.rbac.defaultRoles`: the roles a new user gets;
- `authz.rbac.anonymousRoles`: the roles of the anonymous principal;
- `authz.rbac.serviceRoles`: roles per principal key (`{ 'service:telemetry': ['telemetry'] }`).

## Decision (implemented in L1 task 3)

1. **`anonymousRoles` and `serviceRoles` are assignments the model holds.** The RBAC model reads
   them at `init`. It treats each listed role as a GLOBAL assignment of the matching subjects:
   - `anonymousRoles` go to every subject of type `anonymous`;
   - `serviceRoles` go to the subject whose `principalKey` is the key, companions included, as for
     stored assignments.
2. **A bad role there fails the boot with `AuthzConfigError`.** A role is bad when it:
   - is not defined (`unknown_role`);
   - has `assignable: false` (`not_assignable`);
   - has `scopeTypes` that leave out `'$global'` (`wrong_scope_type`; these assignments sit at
     `$global`, see the L1 task 1 decision).

   A value that is not an array of role names (or, for `serviceRoles`, a map of such arrays) fails
   the boot the same way. The message names the key and the role.
3. **The model does not apply `defaultRoles`.** Users (lane C1) applies it when it creates a user, by
   writing stored assignments through `AuthzAdmin`. The write path then validates it like any
   `assignment.grant` (`unknown_role`, `not_assignable`, `wrong_scope_type`). C1 should also check
   the list once at boot, with `assignmentProblem` at `GLOBAL`, so a bad default fails at start and
   not at the first sign-up.

The alternatives were to ignore a bad config role with a warning (as for stored assignments) or to
refuse only unknown roles. Both were rejected: config is written by the operator and read at boot,
and a broken config should stop the boot (§6.5). Stored rows are data that may outlive a role, so
they are ignored instead (B12).

## Proposed fixture cases (kit owner)

For `B12.rbac` (lanes `['L1']`; facets `engine`, `rbac`), each a boot case
`{ throws: 'AuthzConfigError', message: [<fragment>] }` with `config.rbac` set:

| Case | `config.rbac` | Roles | Message fragment |
|---|---|---|---|
| an unknown anonymous role is refused at boot | `{ anonymousRoles: ['ghost'] }` | `guest` | `ghost` |
| a non-assignable anonymous role is refused at boot | `{ anonymousRoles: ['admin.users'] }` | B12's `ROLES` | `admin.users` |
| an unknown service role is refused at boot | `{ serviceRoles: { 'service:svc': ['ghost'] } }` | `guest` | `ghost` |
| a service role limited to other scope types is refused at boot | `{ serviceRoles: { 'service:svc': ['org.admin'] } }` | `org.admin` with `scopeTypes: ['org']` | `org.admin` |

And one positive case for B11 or B10: a `service:svc` principal holds its `serviceRoles` at GLOBAL
and passes a check that the role grants. B10.rbac already covers `anonymousRoles`.

For C1: a fixture in the users lane that a bad `defaultRoles` entry fails the boot, and that a new
user holds `defaultRoles` as stored GLOBAL assignments.
