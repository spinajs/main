# L4-2: the kit oracle reads a like pattern ending in a lone `\` as the engine does

Status: APPROVED and APPLIED 2026-10-05 (KT1) in the kit oracle; L4 (authz-orm conformance)
drops its exclusion of such values in its own step. Owner of the change: K4 / F5
(`@spinajs/authz-testing`). L4 does not edit the kit.

## Problem

The engine's evaluator, the reference for every residual (`packages/authz/src/engine/evaluate.ts`
`matchLike`), answers `undefined` (UNKNOWN) for a `like` pattern that ends in a lone `\`. The
ORM compiler follows it (conventions §5: "a trailing `\` ⇒ UNKNOWN"). The kit oracle
(`packages/authz-testing/src/filter-eval.ts` `compilePattern`) reads that `\` as a literal
character, so `like 'a\'` is TRUE or FALSE there.

K4 aligned the oracle's coercion with the engine (number strings, booleans and 0/1, boolean
ordering, Dates, non-finite numbers); this case is the one left. Adapter conformance shows it: with
the value `'a\'` among the conformance values, `not (title like 'a\')` selects every non-NULL row
except `a\` (r7) in the oracle and none in SQL, on SQLite and Postgres (`.authz-sdd/L4-t11-conf-mut-backslash.txt`).
L4's conformance keeps such values out until the oracle changes.

## Change

`filter-eval.ts`, where the `like` comparison is evaluated (the caller of `compilePattern`, near
line 142; `compilePattern` only returns tokens): a pattern whose last code point is a lone `\`
makes the comparison UNKNOWN (`null`), as `matchLike` does. Document it next to the other like rules in the
`evaluateFilter` comment.

## Affected lanes

- K4/F5: the oracle change and a unit case.
- L4: drop the exclusion from `packages/authz-orm/test/conformance.test.ts` after the change.
- L7 (or any SQL lane judged by the oracle): the same exclusion, if it has one.
