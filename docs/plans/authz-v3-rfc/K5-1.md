# RFC K5-1: per-request strategies count failures only

Status: PROPOSED. The behaviour ships in K5 without a frozen-contract change; this RFC covers only the frozen doc
comments that now describe the old flow, and an optional move of `peek` into the contract.

Step K5 (controller decision on the N1 final review, finding I1). Frozen contracts:
`packages/authn/src/contracts/strategy.ts` (`AuthenticationStrategy.throttleKeys`),
`packages/authn/src/contracts/throttle.ts` (`AuthnThrottle.attempt`).

## Problem

N1 counted every `authenticate` call in the `login` flow before verify (design §22.4, A05). Per-request
strategies (`TokenStrategy`, `JwtBearerStrategy`, `JwsAssertionStrategy`, `HttpSignatureStrategy`) give an
`account` key per token or key id, and only `succeed` after verify gave the count back. So a client with more
than 5 requests in flight on one valid credential, or more than 20 from one IP, got 401 with `Retry-After`.

The controller decided: per-request strategies count only failed attempts, and the backoff applies after
failures; interactive strategies (password and anything with a login flow) keep counting before verify.

## What K5 did (no frozen file touched)

- `DefaultAuthnService.authenticate`: when every candidate has `interactive === false` and the throttle can
  peek, it calls `peek` before verify (refuses during a delay, counts nothing), verifies, and calls `attempt`
  only after a failure (any non-success: strategy failure, broken strategy, refused status, store error). A
  refused count answers `throttled`. A success still calls `succeed` with the answering strategy's keys, so it
  resets that credential's account key and takes only that credential's `account-ip` count off the ip key
  (H31, D8); other credentials' failures stay on the ip key.
- `PeekableThrottle` / `canPeek` in `packages/authn/src/throttle/peek.ts` (not frozen). `MemoryAuthnThrottle`
  and `DbAuthnThrottle` implement `peek`. A throttle without it keeps the old count-before-verify flow, and boot
  logs a warning when a per-request strategy is listed.
- The kit's `FakeAuthnService` and `FakeBackoffThrottle` follow the same flow; new A05/core and A06/core cases
  and three mutation checks pin it.

## Trade-off (accepted by the decision, stated here)

- `peek` and the count after a failure are two steps, and a count refused by a parallel failure is not recorded.
  So a parallel burst of K wrong credentials is verified in full and adds one backoff step, not K. The K5
  review probe (`.authz-sdd/probes/K5/`, default params, one IP) measured about 39 guesses an hour for the old
  flow, 1,000 with bursts of 50 and 10,000 with bursts of 500.
- That is harmless for the shipped strategies: API tokens carry 256 bits, JWT bearers and key assertions or
  HTTP signatures need a private key. A third-party `interactive: false` strategy over a guessable secret loses
  A05's bound: per-request strategies must take only credentials of 128 bits or more, or signatures.
- While a `MemoryAuthnThrottle` table is full, `attempt` refuses and `peek` does not, so per-request failures
  are verified but not counted until a row frees (the old flow refused them before verify).

## Change (proposed, not applied)

1. Doc comment of `AuthenticationStrategy.throttleKeys`, last two sentences, from

   > … so succeed gives the attempt back and healthy API clients never back off. They count in the 'login' flow
   > like every authenticate call.

   to

   > … Non-interactive strategies count only their failures in the 'login' flow: the service peeks before verify
   > and counts after a failure, so parallel requests on a valid credential never back off (K5). A parallel burst
   > is verified in full, so they must take only unguessable credentials (128 bits or more, or signatures).

2. Doc comment of `AuthnThrottle.attempt`, first sentence, from "Counts the attempt before verification and
   claims its slot atomically" to "Counts the attempt and claims its slot atomically: before verification for
   interactive strategies, after a failure for per-request ones (K5)".

3. Optional: move `peek` into `AuthnThrottle` as an optional member, so every store implements it and the
   no-peek fallback and its warning can go:

   ```ts
   /** Whether a backoff delay holds any of the keys now; counts nothing (the per-request gate, K5). */
   peek?(keys: readonly ThrottleKey[], flow: ThrottleFlow, ctx: AuthnContext): Promise<{ allowed: true } | { allowed: false; retryAfterSeconds: number }>;
   ```

## Affected

- Design §22.4 and §22.13 and rule A05 ("Attempts are counted before verification") need the per-request
  exception, the burst trade-off and the entropy requirement above in their text (D lane). The kit's A05 rule
  title already says it.
- Throttle implementers outside this repo: without `peek` they keep the old behaviour (and the warning).
- N8a: no change; the HTTP layer only maps the result.
