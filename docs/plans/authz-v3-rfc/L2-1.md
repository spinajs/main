# L2-1: the DB stores next to AuthzAdmin (L9 tests, port docs, connection, admin permissions)

Status: proposed (L2, 2026-10-04). Owner of the change: L9 (`packages/authz-rbac/src/admin/**`,
`packages/authz-rbac/test/admin/**`); item 4 may go to the kit instead.

## Problem

L2 task 10 puts L2's DB stores and L9's AuthzAdmin in one package and one mocha process, and runs
AuthzAdmin on `DbAuthzAdminBackend` with the DB stores. Four things need L9 (or the kit).

1. `test/admin/db/backend.test.ts` ("DbAuthzAdminBackend on SQLite") creates `authz_version` by
   hand in its `before` hook. Its comment says the table "belongs to the authz-rbac DB stores'
   migration (AuthzRbac_2026_10_01_00_00_00), not on this branch". That migration is now in the
   package and registers at import with `@Migration('default')`, so the test's `Orm` boot
   (`Migration.OnStartup: true`) creates the table first and the hand-made `CREATE TABLE` fails:
   the whole suite errors in `before all`. L2 cannot fix this on its side without unregistering its
   own migration.
2. `AdminAssignmentStore.forgetScope` (`src/admin/ports.ts`) says it removes rows AT the scope,
   "not rows whose subject is a set at it", and `RbacScopeForgetter` (`src/admin/forgetter.ts`)
   says the same. `DbAssignmentStore.forgetScope` also removes every row whose subject is a set
   living at the scope, wherever it is held, and `DbRuleStore.forgetScope` removes the `allow`
   entries of other rules that name such a set. Two L2 reviews (task 3 I1, task 6) judged that
   leaving them is a security issue: when a scope id is reused, the old grants of its sets come
   back. No L9 handler or test depends on the narrower behaviour with the DB stores: the forgetter
   only turns the returned rows into `RoleRevoked` events and tags, and the tests that assert the
   narrow behaviour or exact `affected` counts (`memory-stores.test.ts`, `canvas.test.ts`) run on
   the memory stores.

   **Question for L9 (and the controller):** with the DB store, `scope.forget` on `org:1` also
   deletes rows held at other scopes, GLOBAL included, whose subject is a set at `org:1`. The
   command is guarded only by its permission at the node, so those deletions pass none of
   `protectSystemRole`, `preventSelfLockout` and `preventLastPrivilegedRemoval`: a row of a
   non-assignable system role, or the last privileged path, can go. It only takes rights away,
   but it should be accepted knowingly, or the guard should review the extra rows (the store
   could report them before deleting). Also, `DbRuleStore.forgetScope` returns only the deleted
   rules: rules that lost an `allow` entry get no `rule:<id>` tag and no `RuleChanged` event. The
   domain version bump keeps caches right (the RBAC model ignores `rule:` tags), but an audit or
   event consumer does not see the change. The port could return the changed rules too
   (`DbRuleStore.forgetScopeEntries` has them).

3. `DbAuthzAdminBackend` opens its transaction on `authz.admin.connection`, else the default
   connection. The DB stores now read `authz.rbac.connection`, else `authz.admin.connection`, else
   the default, so a config that names only `authz.admin.connection` works end to end. A config
   that names only `authz.rbac.connection` (another connection than the default) does not: the
   backend stays on the default connection and the stores refuse its transaction at the first
   write (`AuthzConfigError` naming both keys). Tested in
   `test/integration/stores.db.test.ts`. Either key naming a non-default connection also needs
   the migrations run on that connection: `@Migration('default')` migrates only the default one
   (true of L9's idempotency migration too); without them the first read fails on a missing table.
   A backend built with `new DbAuthzAdminBackend({ connection })` (an option, not config) leaves
   the stores on the configured connection, and they refuse its transaction.
4. The kit's B27.store world (`B27-lanes.spec.ts`) declares only `file:read` and `file:write`, but
   AuthzAdmin checks `authz:assignments.manage` for SYSTEM too, so the part throws
   `UnknownPermission` unless the harness declares the RBAC admin permissions. L2's harness
   declares `authz:assignments.manage`, `authz:links.manage` and `authz:rules.manage` when a
   world lacks them, as an app using the RBAC write handlers must.

## Change

1. In `test/admin/db/backend.test.ts`, drop the hand-made `authz_version` table and its comment
   from the `before` hook; the package migration creates it. (Or guard it with
   `if (!(await db.schema().tableExists(VERSION)))`.)
2. In `src/admin/ports.ts`, reword the `forgetScope` doc to allow the wider removal, e.g.
   "Removes every row AT the scope, and may remove rows whose subject is a set at it (the DB
   store does, so a reused scope id inherits nothing); returns the removed rows." Reword the
   `RbacScopeForgetter` comment to match. Optionally make `MemoryAdminAssignmentStore` remove the
   set rows too, so both stores behave the same. Answer the question above. Also state on the
   ports that `find` without a page returns every match (the DB stores now do; with a page they cap
   at 1000).

3. In `src/admin/db/backend.ts`, default the connection to `authz.admin.connection`, else
   `authz.rbac.connection`, else the default connection, the mirror of the stores' order, so
   either key alone puts the backend and the stores on one connection.
4. Either the kit adds `authz:assignments.manage` to the B27.store world, or L9 declares the
   permissions of its write handlers (for example through an `AuthzContributor` of the RBAC admin
   module), so a domain that wires the handlers needs no extra config. The second also lets L2's
   harness drop its fallback.

No contract or engine change.

## Affected lanes

- L9: the files above.
- Kit owner: B27.store world, if change 4 goes there.
- L2: none further; until change 1 lands, "DbAuthzAdminBackend on SQLite" fails in the package suite
  (reported in `L2-task-10-report.md`).
