Security: a session item whose `ImpersonatorId` or `ExternalKey` attribute is present but cannot be read is now treated as expired: `restore` answers `null`, listings leave it out, `touch` does not extend it, `deleteBySubject(subject)` deletes it without counting it, and a warning names the subject and the attribute (never the session id). Before, it read as "not impersonated" or "no IdP session", so revoking the impersonator's sessions (`deleteBySubject(admin, { includeImpersonations: true })`) or an IdP back-channel logout (`deleteByExternalKey`) could not find it and the session stayed live. Unreadable means: an `ImpersonatorId` that is not an `S` principal key with a non-empty type and id (`N`, `BOOL`, `NULL`, `M`, `L`, `''`, `'admin'`, `':admin'`, `'user:'`), an `ExternalKey` that is not of type `S`. Only an absent attribute means none, which is what the store writes. A `Subject` with an empty id (`'user:'`) is now unreadable like any other unreadable `Subject` (the item reads as absent), instead of a session of the principal `user:""`. `touch` also refuses an item whose `ImpersonatorId` or `ExternalKey` no longer holds the value the caller's session carries. At upgrade, existing sessions keep working: every 3.x version writes an `S` principal key or no `ImpersonatorId`, and an `S` string or no `ExternalKey`. The one exception is a session saved with an impersonator whose type or id is empty (`'user:'`, `':admin'`), which no framework caller writes; it now ends.
