The SQL forms of `rbac.assignment` (list filters and PostgreSQL row level security) no longer treat an assignment whose `expires_at` holds a value the database cannot read as a datetime (SQLite text, a PostgreSQL `infinity`) as live for ever, or a MySQL zero date by its month: such an assignment grants nothing, and a deny role it assigns stays in force, as checks already decide since the previous fix; the policies `authz:rls` generates keep a deny of such a row in force too. The stores also read such a value whatever the database's order makes of it, so the model refuses it instead of the SQL filter dropping it (a PostgreSQL `-infinity`, a MySQL `0000-00-00`, SQLite text such as `''`): before, a deny assignment, a rule or a set membership holding one vanished from checks. A PostgreSQL `infinity` written by hand for "never" must be set to `NULL`. Row level security policies are SQL that `authz:rls --out <dir>` wrote into a migration, so they keep comparing `expires_at` as before until they are replaced. A regenerated migration creates the policies again and fails on a database that holds them (`policy … already exists`): run the `DROP POLICY IF EXISTS …` statements of the old `AuthzRls_*` migration's `DOWN` list, then `migrate-up` with the new one, in one deployment step (in between the tables keep `FORCE ROW LEVEL SECURITY` with no policy and show no rows).
