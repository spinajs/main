`ServerResponseMapper` has a new method `insertedKeys(response, insert)`: the primary key of every row an insert wrote, in insert order, as one object per row (key column name to value), or `undefined` when the dialect cannot tell. It is all or nothing, never a partial list. `ModelBase.insert()`, the static `Model.insert()`, the unit of work and the write capture take the keys of inserted rows from it, so a connection package decides them by overriding it in its mapper.

The default reads the `RETURNING` rows of `read()` when there is one per inserted row with the whole key, projected to the key columns. Otherwise it keeps the rule core applied before, now in one place: `LastInsertId` for a single-column `auto` key whose column is `AutoIncrement`, and `LastInsertId + index` for several rows only on a driver that reports `insertIdIsFirstOfBatch`, for one statement without ignore, replace or update on conflict, no supplied key and `RowsAffected` equal to the row count. An insert builder without a model has no known keys.

`ModelBase.insert()`, the static insert and the unit of work no longer set a model's key from `LastInsertId` when the key column is not `AutoIncrement`, or when `LastInsertId` is not a positive integer; such a key stays unset after an insert without `RETURNING`. Before, a MySQL or MSSQL model whose key the database fills another way got `0` or another column's identity value as its key. A key the caller supplied is never overwritten, also not by `RETURNING` rows. The unit of work no longer throws `OrmException` (`insert of <Model#key> returned no generated key ...`) when a driver reports no identity value: the key stays empty. The write capture reports the same keys as before, with one exception on MSSQL: a single-row upsert whose row carries no conflict value is keyed by its `SCOPE_IDENTITY()` value, which `MsSqlServerResponseMapper.read()` reports, instead of reaching observers with `unknownKeys: true`.
