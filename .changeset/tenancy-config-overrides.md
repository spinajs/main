A tenant overrides the configuration paths listed in `tenancy.config.overridable`: inside its scope `Configuration.get` answers the values of its `settings` for them (`TenantConfigurationOverlay`): a value at a path a configuration schema declares as the schema accepted it, a value at a path no schema declares as stored (list only declared paths); a stored value holding a `__proto__`, `constructor` or `prototype` key is refused. A listed path under a closed root (`tenancy`, `db`, `authz`, `authn`, `audit`, `fs`, `system`, `process`, `configuration`, `configuration_db_source`, `https`, `logger`, `telemetry`, `otel`, `cache`) or with a `__proto__`, `constructor` or `prototype` segment fails the boot, and so does a key under `tenancy.config` other than `overridable`; a stored value at a path that is not listed is never served. `admitTenant()` and `forEachTenant()` load the tenant's settings into the process; `loadTenantSettings()` does it for code that enters a tenant without an entry point, and a read of an overridable path for a tenant not loaded throws `TenantSettingsUnavailable`. `checkTenantSettings()` validates settings against the configuration schema and refuses a value holding such a reserved key. Without overridable paths no read answers differently; once the package is imported, every configuration read asks the overlay whether it covers the path, which costs a path-cache and a root lookup (measured about 10 ns per read).
