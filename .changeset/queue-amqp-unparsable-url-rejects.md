Breaking: a `host` URL with an unencoded `@` in its vhost or query (`amqp://broker/team@x`), which dialled before, is now refused at boot: write the `@` as `%40` (`amqp://broker/team%40x`). It cannot be told apart from a password with an unencoded `/`, `?` or `#`, which put a piece of the userinfo on the resolver as the host name.

Security fix: a `host` URL that cannot be dialled as written is now refused at once, instead of being dialled and failing at the resolver. Before, a `host` with `://` that `new URL()` rejects was dialled as a host name, whole, so the user name and password in it were handed to the system resolver as the name to look up (and, depending on the resolver, on to a DNS server). The usual cause is a password with an unencoded `/`, `?` or `#`: in `amqp://user:pa/ss@broker` the host part ends at the `/`. A URL that parses but has an `@` after the host (`amqp://user/ss@broker`) had the user name, or the start of the password, looked up as the host. Now `resolve()` rejects with `InvalidArgument('Queue connection <name> has a host that is not a URL: <not a URL>')` before any connect or lookup, and the second form adds the hint to percent-encode. A `host` without `://` that holds an `@` (`user:password@broker`) is refused the same way, with the hint to write it as `amqp://user:password@broker/vhost` or to set `login` / `password`: dialled, the whole value would have gone to the resolver as the host name. Nothing is retried, because the configuration cannot work. Write a `/`, `?`, `#` or `@` in the user name, password, vhost or query percent-encoded (`%2F`, `%3F`, `%23`, `%40`: `amqp://user:pa%2Fss@broker`), or set `login` / `password` instead of putting credentials in the URL. A URL with an unencoded `@` in the vhost or query (`amqp://broker/team@x`) is refused too: write it `%40`.
