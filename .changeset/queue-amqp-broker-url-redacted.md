Security fix: the broker URL's credentials no longer reach the logs. Before, `connect()` logged `host` as configured at `info` (`Connecting to AMQP queue at amqp://user:password@broker/vhost?… with client-id: …`) on the first connect and again on every reconnect, and the connect error quoted it too: `Cannot connect to AMQP queue server at amqp://user:password@…`, which `resolve()` rejects with and which every failed reconnect logs at `error`, so the password reached every log target each `reconnectDelay` while the broker was down. A `host` that `new URL()` rejects also reached the error's cause raw, inside the lookup error (`getaddrinfo ENOTFOUND amqp://user:password@…`). Now the line and the error print the broker as scheme, host, port and vhost only (`amqp://broker:5672/vhost`), without the userinfo and the query (so a `?heartbeat=` setting is not shown either), and a `host` that does not parse as `<not a URL>`. A `host` without `://` prints as `amqp://<host>:<port>/<options.vhost>`. The connect error's cause carries only the client error's name, `code` (`ECONNREFUSED`, `ENOTFOUND`, ...) and its message with every echo of the URL redacted, so a refused connection, a refused login (`403 (ACCESS-REFUSED)`), a missing vhost and a timeout still read apart. Rotate a password that was ever part of a `host` URL, and prefer `login` / `password` over credentials in the URL.
