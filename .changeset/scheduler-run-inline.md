`SchedulerService.runInline(schedule, fn, opts?)` is new: it runs `fn` in the calling process as a `manual` run of the schedule, under the run lease and heartbeat, never retries it automatically, and returns or rethrows its result. It takes the schedule lease and throws the new `ScheduleOverlap` (a `RunConflict`) when another run holds it; a `runOn: 'all'` schedule runs without it but at most once per replica at a time. An error carrying `crash: true`, from `fn` or from the scheduler's own writes, leaves the run and its leases untouched and is rethrown; loop runs follow the same contract: after a crash, in a step or not, the run and its step stay `running`, nothing more is journaled or finalized and no lease is released. On this replica the scheduler loop does not start or claim a run of a `runOn: 'all'` schedule while an inline run of it is in progress. A schedule declared after boot is adopted on first use, and a pruned schedule row is inserted again.
