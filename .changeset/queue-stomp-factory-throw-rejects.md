A websocket factory that throws, or that returns no socket (an `async` factory included), no longer hangs `StompQueueClient.resolve()`. This covers an `options.webSocketFactory` and a `createWebSocket()` override. Before, the factory ran inside the stompjs connect loop, which nothing awaits: `resolve()` never settled, so `QueueService` boot hung, and a throw reached the process as an unhandled rejection with its text unredacted (Node prints it to stderr, or `@spinajs/log` logs it at `fatal` with the raw error). A throw on a reconnect stopped the client from reconnecting at all.

Now such a factory, before the first connect, rejects `resolve()` at once with `InvalidArgument("Queue connection <name> cannot open a websocket to <broker>: <reason>")`. Both the broker and the reason have the broker's userinfo, query and secret path parts masked. For an `async` factory the reason says it returned a promise, and the promise's own error is not quoted. A socket that such a factory resolves to later is closed. A throw on a later reconnect is logged at `error` the same way, and the client tries again after `reconnectDelay`. stompjs arms its `connectionTimeout` watcher before the factory runs, and its `deactivate()` does not clear it, so the watcher stays alive for up to `connectionTimeout` ms after such a rejection.

**Breaking:** `options.webSocketFactory` counts only when it is a function. Before, `webSocketFactory: null` (or an explicit `webSocketFactory: undefined`) made stompjs open the socket with the global `WebSocket` (Node's built-in one, or whatever the application assigned to `globalThis.WebSocket`). Now any value that is not a function means the transport's own `ws` socket, as when the key is unset, and a host that `ws` cannot open rejects at boot. An application that used `null` to get the global `WebSocket` now connects through `ws` and bypasses a global replacement; pass `webSocketFactory: () => new WebSocket(host, Versions.default.protocolVersions())` to keep the global one.
