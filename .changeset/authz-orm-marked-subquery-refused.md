A statement that embeds a query carrying `.accessible()`, `.within()`, `.withAccess()` or `.withFields()` as a sub-query is refused with `AuthzConfigError` before any SQL is sent. Before, the mark on the sub-query was ignored without a word: only the query that executes runs the access list, so `Plain.query().whereIn('task_id', Task.query().select('id').accessible('task:read'))` returned the rows that point at tasks the caller may not read, `whereExist(Task.query().accessible(...).where(...))` told whether a forbidden row exists, and an update or delete with such a `whereIn` changed rows selected through forbidden tasks. Every place a select sits inside another statement is checked, depth first: `whereIn` / `whereNotIn` / `whereExist` / `whereNotExists` with a query, the relation forms of `whereExist` (belongsTo, hasMany, the junction select of a many-to-many), nested groups, join callbacks, `selectCondition()` columns and to-one populate callbacks, in selects (also `first()`, counts, `resultExists()`, pages), updates and deletes.

An application that put one of these marks on a sub-query now gets `AuthzConfigError` where it silently got unfiltered rows. Execute the marked query on its own and pass its result as values: `const ids = (await Task.query().select('id').accessible('task:read')).map((t) => t.id); Plain.query().whereIn('task_id', ids)`. A mark on the outer query keeps working, and an unmarked sub-query compiles to the same SQL as before. `.unscoped()` on a sub-query is not refused. A later release applies marks on sub-queries instead of refusing them.
