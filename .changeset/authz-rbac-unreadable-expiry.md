An `expires_at` of an assignment, a set membership, a rule or a share link that holds a value no datetime converter reads (text, a MySQL zero date, a PostgreSQL `infinity`) no longer reads as "never expires", and, when the store reads the row, never as "expired" where that would lift a restriction: the checks that meet such an assignment fail closed (`model_error`, the assignment id in the log), and every check of its principal does when it makes the principal a member of a subject set (the set may deny); such a rule refuses the checks of its path and the lists of a permission it can match (every rule narrows); such a link is refused as unknown; a membership read that meets such a row throws `AuthzConfigError`; a membership recompute (`AuthzAdmin` writes, `authz:membership-rebuild`) refuses such an assignment when its role makes a set member, instead of writing a membership that never expires; a new expiry on such a row is checked as a grant; the protected-role check of `@spinajs/users` counts its role as held. Before, such a row was a permanent grant. Behaviour change for 3.x users: a row written by hand with PostgreSQL `infinity` for "never" must be set to `NULL`. Before upgrading, run the finder queries of `docs/authz-rbac/02-database-storage.md` ("Unreadable `expires_at`") and repair what they list. Until a row is repaired, a grant it holds ends, and a deny role or a rule it holds stops the checks that meet it with `model_error` (the log names the assignment or the rule) instead of being dropped. After upgrading, run `authz:membership-verify`: a membership recomputed before this release from such an assignment is stored as never expiring; the command refuses, naming the assignment, until it is repaired, and then lists the membership as changed; `authz:membership-rebuild` rewrites it. Not yet covered (a follow-up fix): a value the database sorts before now (PostgreSQL `-infinity`, a MySQL `0000-00-00`) is still dropped by the stores' SQL filter, so a deny assignment or a rule holding one does not apply in checks; and lists filtered by the policy plan (`rbac.assignment`) and PostgreSQL row level security still keep a value it sorts after now live until it is repaired.
