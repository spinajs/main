`integrity: 'sealed'`: `AuditSealTask` (every 60 seconds, leader only) and `sealAudit()` hash the events of a sealed trail in `seq` order into chained seals in `audit_seal`, per table and connection, at the archive for a shipping trail. A run seals what was already there 30 seconds earlier (`audit.seal.settleSeconds`), so an event is sealed within about two minutes. `settleSeconds` must exceed the longest time an audited row sits between its insert and its commit (a transactional write in a long transaction): a row that commits later lands in a range already sealed, where verification reports it for good; `sealAudit({ settleMs: 0 })` is for tests. A seal's range starts where the previous one ended, so a second seal chained from the same seal is refused. A run adds at most `audit.seal.maxSeals` (default 100) seals per table, and `AuditSealTask` has a 10-minute timeout. `SealFailure` carries a `reason`: a sealed trail whose store keeps no table (a log store, an outbox trail with neither archive nor sink) is reported there and logged, as is a `seq` reset below the end of the seal chain (a re-created table, MySQL 5.7 after retention emptied it) and a concurrent sealer; a shipping trail without an archive here is skipped silently, since the service that holds its archive seals it. Each seal is read and written in a transaction of its own, so a row of a caller's open transaction is never sealed before it commits. `@spinajs/audit` exports `eventDigest` and `sealHash` next to `payloadHash`. Retention on a sealed table removes whole sealed ranges and keeps their seals, marked pruned; events not sealed yet stay. Declare `AuditSealTableMigration` on every connection that holds a sealed table; a trail may not use `audit_seal` as its table.
