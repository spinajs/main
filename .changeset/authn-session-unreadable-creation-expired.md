Security: the framework no longer hands a store an expiry it would save as "never expires". When an expiration strategy computes an instant that is not valid, or the session's `Creation` cannot be read, `SessionProvider`'s expiration helpers now set `Expiration` to the epoch (a real instant that has passed) instead of the invalid `DateTime`; `session-provider-db` wrote that invalid value as SQL `NULL` and `session-provider-redis` as a missing expiry, so a `SlidingCappedExpiration` renewal or an `AbsoluteExpiration` initial expiry over an unreadable `Creation` could make a session immortal. `SessionProvider.isExpired()` also counts a session whose `Creation` cannot be read as expired, whatever its `Expiration`, so every store refuses such a row on `restore` and leaves it out of listings, and `DefaultSessionIssuer.restore` no longer reaches the strategy (which threw for the db store's `null` `CreatedAt`). A valid session's expiry is unchanged, and an absent expiry from a strategy still means "never". An application that calls a store's `save` itself with an invalid `Expiration` is not covered by this: `session-provider-db` still stores that as "no expiry" until its own fix, and `session-provider-redis` until its read of a present `null` expiry lands.
