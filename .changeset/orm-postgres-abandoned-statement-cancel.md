A statement outside a transaction that got no answer from the server (pg's client-side `query_timeout`) is now cancelled on the server when its client is destroyed: the driver sends PostgreSQL's cancel request with the backend's process id and secret key, so the backend stops running it and a write it was making rolls back. Repeated timeouts no longer leave one busy server connection per abandoned statement beside the pool. A stream whose read fails without a server answer is cancelled the same way. The cancel is best effort and fire and forget: it waits at most `Pool.AcquireTimeout` (5 s when that is 0), a failure is logged at `debug`, and the caller still gets the timeout; a server that sent no usable cancel key gets one `warn` per process and no cancel. `Options.CancelAbandonedStatements: false` turns it off. Not covered: statements inside a transaction, a pooler such as PgBouncer (the client's connection is closed before the cancel arrives), a TLS-terminating proxy or a server that refuses plain connections (the cancel is plain TCP), a custom `stream`, a cancel key longer than 32 bits, and a statement that finished before the cancel arrived. A server-side `statement_timeout` below `query_timeout` stays the recommended first line.
