A write and `authz:ancestors-rebuild` link a resource only to parent rows that exist (soft-deleted and archived rows count; a parent type no model of the process registers is linked as written). Links to a parent id with no row, which writes and rebuilds used to write, are no longer written, so a grant made on such an id stops reaching the children until a row with that id exists. Inserting a row links every resource whose `@Parent` column already names its id: a child written before its parent gets its links when the parent arrives, and a reused id inherits the children that still name it, through a write or a rebuild alike. Writes and a quiet rebuild now leave the same table. Each insert of a type that a `@Parent` column names runs one more select per such column (index those columns; an insert of a type without `@Parent` of its own also takes the write capture's key read, which it did not before). With db.WriteCapture.MaxRows set, such an insert above the limit is now refused, and an upsert of such a type runs in a transaction. Each write that links a parent runs one select per class table of the parent's type. Major: an application's access can change.
