Security: `SafeFetch` refuses a URL that carries a user name or a password (`https://user:secret@host/...`) before it calls `fetch`, with `InvalidArgument('URLs with a user name or password are not fetched')`, which quotes nothing of the URL. Before, `fetch` threw `TypeError: Request cannot be constructed from a URL that includes credentials: <URL>` with the whole URL in the message (user name, password and query string), and `SafeFetch` rethrew it. For a list source in `emailVerification.lists.sources[].url` with userinfo, that message was the sync outcome's `error`: it went to the `email-verification` warn line `List <name> sync failed, the old list stays: …`, to the output of the `email-verification:sync` command, and into the scheduler task's error `list sync failed: <name>: …`. For a provider in `emailVerification.http.providers[].url` it went to the warn line `Domain check provider <name> failed: …`, once per checked domain. For `emailVerification.rdap.bootstrapUrl`, with `RdapVerifier` listed in `verifiers`, it went on each bootstrap attempt to the service's warn line `Verifier rdap failed for <domain>: …` and to the `email-verification:check` output. A URL without userinfo was never quoted by these lines. If a configured URL held a user name or password, treat that password as exposed in those logs and outputs: rotate it, and move the secret to `headers` (providers) or a query token (list sources). Such a source now syncs as `failed` with the new message, and such a provider answers unknown.
