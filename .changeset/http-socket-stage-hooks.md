Command stages get generic hooks. `SocketCommandStage.onRegister?(handler, registration)` runs once per command when the registry builds, in `Order`, after every command registered (names unique, policies resolved, contract and payload validators attached) and before socket.io attaches; a throw fails the build with an `InvalidOperation` naming the stage and the command. `registration.refuseStream(what)` refuses an async-generator handler at registration and an async-iterable result at run time (`handler.streamRefusal`, the highest `Order`'s word). The command context gains `handlerStarted`, `drainGrace` (spared by the shutdown drain's first abort once the handler started) and outcome recorders (`addOutcomeRecorder`, `recordOutcome`, `detachOutcome`). `ISocketCommandContext` gains them as required members, which is a type break for classes that implement it (none exist outside the package).

An abort before the handler started now stops the chain: `next()` rejects with the new `SocketClientGone` (`beforeHandler: true`, the abort reason as `cause`), a `SocketException` with the abort reason's code and message, so the client's answer is unchanged, and no later stage or handler runs. That holds also when a later stage was waiting on the abort (the connect hooks, an idempotency join, the ordering queue, where a queued command rejects when its turn comes). After the handler started, `next()` still settles with the handler's real outcome; only an `ordered` command cut loose after `ordering.abortGraceMs` rejects the stages before the ordering stage with the abort reason itself. A custom stage that compared the rejection with `ctx.signal.reason` should check `err instanceof SocketClientGone` (and read `err.cause` for the reason). A second `next()` call from one stage rejects with `internal` `next() called twice by <Stage>`.
