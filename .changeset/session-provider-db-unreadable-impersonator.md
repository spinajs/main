Security: a `user_sessions` row whose `ImpersonatorId` is present but is not a principal key with a non-empty type and id (`''`, `user:`, `:admin`, `admin`, `42`, a SQLite blob) is now an expired session: `restore` answers `null`, listings leave it out, `touch` does not extend it, and a warning names the subject and the column (never the session id). Before, it read as "not impersonated", so revoking the impersonator's sessions (`deleteBySubject(admin, { includeImpersonations: true })`), which selects by equality on that column, missed it and the session stayed live. The same holds for a SQLite blob in `ExternalKey` and an IdP back-channel logout; any text there is still a key. A `Subject` with an empty type or id now reads as no owner. `touch` now also requires the stored `ImpersonatorId` to match the session it renews. At upgrade, existing sessions keep working: every 3.x version writes `ImpersonatorId` as a principal key or `NULL` and `ExternalKey` as text or `NULL`; 2.x had no such column. The one exception is a session saved with an impersonator or subject whose type or id is empty, which no framework caller writes; it now ends.
