# Query clone defects: statement rebinding and RBAC constraint loss

Two defects, one root cause family: **`clone()` copied statements without rebinding them to the
builder they now belong to.** Defect A is the direct form (a statement kept the source
builder). Defect B is the transitive form (a correlated EXISTS sub-query kept a closure over
the source builder, and the predicate never reached the clone at all).

Both fixed in the framework. No consumer controller was touched.

Committed as `8f17057e1 fix(orm): rebind cloned statements to the builder they are handed`, on
branch `fix/query-clone-statement-rebinding` off `origin/master`. (The framework working copy was
sitting on `fix/swagger-wire-schemas`, three unrelated commits ahead of master; the fix was moved
to its own branch rather than folded into that one. No files overlap between the two.) The
consumer repo has no tracked change and therefore no commit — see below.

---

## Defect A — a cloned statement compiles the alias of the query it was cloned from

### Mechanism

`packages/orm-sql/src/statements.ts:180-185` (before the fix):

```ts
public clone<T extends QueryBuilder | SelectQueryBuilder | WhereBuilder<any>>(_builder?: T): SqlWhereStatement {
  return _carryQuoter(
    new SqlWhereStatement(this._column, this._operator, this._value, this._builder),
    this,
  );
}
```

`_builder` is accepted and dropped; the clone keeps `this._builder`, the **source** builder.
`SqlWhereStatement.build()` reads the alias off that reference at COMPILE time
(`packages/orm-sql/src/statements.ts:204`, `this._builder.TableAlias`), not at clone time.

The alias is normally assigned *after* the clone is taken:

- `SelectQueryBuilder.clone()` — `packages/orm/src/builders.ts:1169` — copies `_statements`
  and passes the new builder to each `clone(builder)` call precisely so the copies rebind.
- `populate()` calls `setAlias()`, which stamps `$Model$` onto the ORIGINAL only
  (`packages/orm/src/builders.ts:1155-1167`).

So the pagination shape used by ~24 consumer controllers —

```ts
const query = Model.select().filter(...);
const cQuery = query.clone();          // no alias on either query yet
const rows  = await query.populate(include).take(...);   // assigns `$Model$` to `query`
const count = await cQuery.selectCount();                // compiles `$Model$` into cQuery
```

— produced a COUNT query naming an alias its own `FROM` never declares.

### Wire proof (pre-fix)

```
GET /player-content/groups?filter=…name like 'owned'…&include=["entries"]   -> 500
  ER_BAD_FIELD_ERROR 1054: Unknown column '$EntriesGroup$.name' in 'where clause'
  SELECT COUNT(*) as `count` FROM `yourscreen-db`.`player_content_entries_group_view`
    WHERE ( `$EntriesGroup$`.`name` LIKE '%owned%' ) LIMIT 1

GET /player-content/groups/159/entries?include=["Group"]                    -> 500
  ER_BAD_FIELD_ERROR 1054: Unknown column '$ContentEntries$.group_id' in 'where clause'
  SELECT COUNT(*) as `count` FROM `yourscreen-db`.`player_content_entries`
    WHERE `$ContentEntries$`.`group_id` = 159 LIMIT 1
```

The emitted SQL is the mechanism written out: the count query is the clone, and it names the
alias the populated original declared.

## Defect B — a cloned query's RBAC EXISTS loses its correlation entirely

Not the same mechanism as A, though it lives in the same `clone()` contract. The hypothesis
in the brief (clone bypasses the container / the middleware never runs on the clone) is
**wrong**, and was ruled out before changing anything:

- `Builder`'s constructor resolves the middlewares itself (`packages/orm/src/builders.ts:66`,
  `this._queryMiddlewares = DI.resolve(Array.ofType(QueryMiddleware))`), and
  `SelectQueryBuilder`'s constructor runs `afterQueryCreation` (`builders.ts:1147`). `clone()`
  then *overwrites* `_statements` with clones of the source's statements — which already
  contain the RBAC constraint. So the clone does carry an RBAC statement.
- The constraint is lost when that statement is **compiled**, not when it is created.

### Mechanism

`RbacModelPermissionMiddleware.afterQueryCreation` (`packages/rbac/src/middleware.ts:184-189`)
calls the model's `rbac` hook. In the consumer both hooks are `whereExist`-shaped:
`EntriesGroup.rbac` → `whereExist("Owners", …)`, `ContentEntries.rbac` → `whereExist('Group', …)`.

`whereExist` dispatches to an `ExistsRelationHandler`
(`packages/orm/src/existsRelationHandlers.ts`). Every handler built its correlation predicate
as a **lazy** statement — necessarily, since the outer alias may not exist yet — and the lazy
callback wrote to the sub-builder captured in its closure:

```ts
const relQuery = junctionModel.query().setAlias(`${junctionTableName}_exists`);
relQuery.where(
  Lazy.oF(function () {
    relQuery.where(new RawQuery(`${rel.JunctionModelSourceModelFKey_Name} = ${sourcePKeyRef(builder, tDesc)}`));
  }),
);
```

That only ever worked by a side effect the compiler was written to tolerate —
`packages/orm-sql/src/compilers.ts:271-276` builds lazy statements first *"so the non-lazy pass
below can pick up any statements the lazy build appended"*. `SqlLazyQueryStatement.build()`
itself returns nothing useful: it evaluates the callback against a scratch clone
(`statements.ts:59-65`) and reads `context.Statements`, which the callback never writes to.

On a clone this collapses:

1. `SqlExistsQueryStatement.clone()` (`packages/orm-sql/src/statements.ts:562`, pre-fix) built
   `new SqlExistsQueryStatement(this._builder.clone(), this._not)` — a NEW sub-builder — and
   ignored the `_parent` it was handed.
2. The cloned sub-builder's lazy statement still closed over the ORIGINAL `relQuery`.
3. Compiling the clone ran the callback, which appended the correlation predicate to the
   original's sub-builder. The clone's own statement list stayed empty.
4. Result: `EXISTS ( SELECT * FROM junction … )` with **no correlation** — true for every outer
   row, i.e. the `readOwn` constraint degenerates to "any owner row exists anywhere".

Reproduced at the SQL level before any change (`RelationModel3.whereExist('Models', …)`):

```
ORIGINAL: … WHERE EXISTS ( SELECT * FROM `JoinTable` … WHERE owner_id = `RelationTable3`.`Id` )
CLONE   : … WHERE EXISTS ( SELECT * FROM `JoinTable` … )                <-- correlation gone
```

Since only the count query is a clone, the rows were restricted and the count was not.

### Wire proof (pre-fix, ground truth from the DB: user 7 may see 1 of 2 groups and 14 of 15 entries)

```
GET /player-content/groups   as readOwn   -> 200  rows=1   X-Total-Count=2    (leaks 1 group)
GET /player-content/entries/ as readOwn   -> 200  rows=10  X-Total-Count=15   (leaks 1 entry)
GET /player-content/groups   as readAny   -> 200  rows=2   X-Total-Count=2
GET /player-content/entries/ as readAny   -> 200  rows=10  X-Total-Count=15
```

## Statement classes audited for the "accepts a builder, ignores it" shape

Every `clone()` in the ORM and in every driver package was read. The rule applied: **a statement
that holds a live BUILDER reference must rebind it; a statement that holds only an alias VALUE
must not.**

### Rebinding was missing — fixed

| Class | File | Held reference | Was |
|---|---|---|---|
| `SqlWhereStatement` | orm-sql/src/statements.ts | `_builder` | accepted `_builder`, kept source |
| `SqlLazyQueryStatement` | orm-sql/src/statements.ts | `context` | no parameter at all |
| `SqlWithRecursiveStatement` | orm-sql/src/statements.ts | `_query` (the OWNING query, which `build()` mutates) | no parameter at all |
| `SqlExistsQueryStatement` | orm-sql/src/statements.ts | sub-select correlation | accepted `_parent`, ignored it |
| `SqlWhereQueryStatement` | orm-sql/src/statements.ts | nested `WhereBuilder` | passed `_parent` through, but crashed on `undefined` |

### Already correct — verified, unchanged

- `SqlInStatement` — `new SqlInStatement(…, (parent ?? this._builder))`.
- `SqlJoinStatement` — `builder: (parent as SelectQueryBuilder) ?? this._options.builder`.

### Correctly do NOT rebind — they hold no builder

`SqlBetweenStatement`, `SqlGroupByStatement`, `SqlColumnStatement`, `SqlColumnMethodStatement`,
`SqlInSetStatement`, `SqlRawStatement`, `SqlColumnRawStatement` (orm-sql), plus the per-driver
`MySqlInSetStatement` (orm-mysql/src/statements.ts:33), `SqliteInSetStatement`
(orm-sqlite/src/statements.ts:49) and `MsSqlInSetStatement` (orm-mssql/src/statements.ts:35).

These carry the table alias as a snapshotted VALUE. `SelectQueryBuilder.setAlias()` re-stamps
that value onto every statement of the builder that owns it
(`packages/orm/src/builders.ts:1162-1164`), so a clone follows its own builder's alias without
needing a reference. Rebinding them would in fact be *wrong*: `clone()` copies statements before
it copies `_tableAlias`, so adopting the parent's alias at clone time would read `undefined`.
This reasoning is now recorded as a block comment above the statement classes in
`packages/orm-sql/src/statements.ts`.

The three driver packages define no other statement subclasses (`grep` for
`extends *Statement` across `packages/*/src`), so the audit is complete.

## The fixes

### `packages/orm/src/builders.ts`

- `SelectQueryBuilder` gains `_correlationSource` + `CorrelationSource` getter +
  `correlateWith()`. This is the outer builder a correlated EXISTS sub-query points at. It is a
  **field rather than a closure variable specifically so `clone()` can rebind it**.
- `SelectQueryBuilder.clone()` restores `_table`, `_tableAlias` and `_correlationSource`
  **before** cloning statements (statements rebind and may read them), instead of after.
- `WhereBuilder.clone()` likewise restores `_model` / `_tableAlias` / `_boolean` before cloning
  statements — `WhereStatement`'s constructor re-validates its column against `builder.Model`,
  and a nested where-builder whose model differs from the parent it re-attaches to used to
  throw `column X not exists in model Y`.
- `WhereBuilder` gains a `Parent` getter, so a statement owning a nested where-builder can
  re-attach a clone to the same parent when it is cloned without being handed one.

### `packages/orm/src/existsRelationHandlers.ts`

- All three handlers call `.correlateWith(builder)` on the sub-query they build.
- All three lazy callbacks now push their predicate onto **`this`** — the builder the lazy
  statement is being compiled for — instead of the captured `relQuery`. This is what makes the
  predicate appear in the clone's own output rather than being appended to the original.
- The outer alias is resolved through `correlationSource(this, builder)`: the context's
  (rebound) `CorrelationSource` first, the captured builder only as a fallback.

### `packages/orm/src/interfaces.ts`

`ISelectQueryBuilder` declares `CorrelationSource` / `correlateWith`.

### `packages/orm-sql/src/statements.ts`

The five clone implementations listed above now rebind, each with a comment naming the failure
it prevents, plus the block comment documenting the whole `clone(parent?)` contract and which
statements participate.

## Not done / notes

- `packages/worker` in the consumer still does not build (`@spinajs/queue-sqs-transport` not
  installed). Pre-existing, unrelated, does not affect the API.
- `packages/orm-api` and `packages/orm-http` keep their pre-existing `fs`-registration test
  failures.
- `SelectQueryBuilder.clone()` still constructs with `new SelectQueryBuilder(...)` rather than
  through the container. No driver registers a `SelectQueryBuilder` subclass today, and the
  middleware list is resolved inside the constructor either way, so this is not currently a
  defect — but it does mean a future driver-specific builder subclass would be silently
  downgraded by `clone()`. Left alone as out of scope.
